# Client-server protocol

Everything a client can send to the server and everything the server sends back: the Colyseus rooms with their
requests, responses and pushes, and the HTTP API behind the GM panel. The Unity WebSocket backend implements this
contract. The battle event stream is in [`BATTLE_EVENTS.md`](BATTLE_EVENTS.md), the combat rules in
[`BATTLE_RULES.md`](BATTLE_RULES.md), the security model in [`SECURITY.md`](SECURITY.md).

Any change to a message must be made here and in the Unity WebSocket handler and DTO.

## Conventions

Colyseus 0.18 request/response. Every client-to-server operation is a request:

```csharp
// Colyseus Unity SDK 0.18
var room = await client.JoinOrCreate<MapState>("map", new Dictionary<string, object> { ["accessToken"] = token });
var res = await room.Request<object>("stage/validateStart", payload); // Dictionary / JObject
```

- **Responses** always resolve; the promise only rejects on transport problems or an unknown request type. Success is
  `{ "ok": true, ...data }`. Failure is `{ "ok": false, "error": "CODE", "extra"?: {...} }`; some rooms add a few
  fields, documented with the room. Clients branch on `ok` and localize `error`.
- **Payloads** are validated with strict schemas. Unknown fields (`userId` included, because identity always comes
  from the token) are answered with the room's invalid-payload code.
- **Authentication.** Every room except `auth`, `chat_directory` and `chat` with `listOnly` needs the join option
  `accessToken`, the access token issued by the `auth` room. An invalid token fails at join time (Colyseus
  `ErrorCode.AUTH_FAILED`: the matchmaking call answers HTTP 525 "onAuth failed"); the Unity client then renews the
  access token once and retries. A room re-checks the session when a request arrives and the last check is more than
  5 s old, and the presence heartbeat checks it as well. A revoked session answers `UNAUTHORIZED`, and the presence
  room closes the socket with 4401. Revocations (ban, GM kick or sign-out, `logout`, `logout_other_devices`,
  `change_password`, `request_deletion`) are also published to every room, which closes that player's connections
  whose session is gone with 4401 at once. The device that asked for `logout_other_devices` or `change_password`
  keeps its connections.
- **Rate limits.** A client that is too fast gets `RATE_LIMIT` (`AUTH_RATE_LIMIT` in `auth`).
- **Join refusals.** Too many room joins per account in a short time answer HTTP `429 RATE_LIMIT` from the matchmaking
  call. An account over its connection cap (`MAX_CONNECTIONS_PER_USER`, 64 in total, and
  `MAX_CONNECTIONS_PER_USER_PER_ROOM`, 8 per room type) gets `TOO_MANY_CONNECTIONS` as the join error. Keep one
  connection per room type per device (the Unity client does) and leave rooms you no longer need.
- **Server pushes** (chat, presence, notices) are plain messages: `room.OnMessage<T>(type, ...)`.
- **Requests only.** Every operation must be sent with `room.Request`. A fire-and-forget `room.Send` of a request type
  carries no request id, so the server ignores it: nothing runs and nothing is answered.
- **Idempotent requests (`requestId`).** `summon`, `power_up`, `evolve`, `sell`, `expand` (roster), `awaken` (not for
  `preview`), `runes/upgrade` and `stage/validateStart` accept an optional `requestId`: a string of 1 to 64 characters
  from `[A-Za-z0-9_-]`, generated by the client once per user action. The server stores the response of the first
  successful call per (user, `requestId`) in the same transaction as the mutation (`user_request_results`, purged after
  `REQUEST_RESULT_RETENTION_DAYS`, default 7). A repeated id returns that stored response unchanged plus
  `"replayed": true` and runs nothing again; this also holds while the first call is still in flight, in which case the
  second call waits for it. Failed calls store nothing, so a retry with the same id runs again. Reuse the id when a
  request is retried after a timeout or a dropped socket, and use a new id for a new action. An id used for a different
  kind of request answers `REQUEST_ID_CONFLICT`. The stored response is the first one: its `wallet` is the balance at
  that time, and a stage ticket in a replayed `stage/validateStart` may already have been used by `battle_start`.

## Common error codes

| Code | Meaning |
| --- | --- |
| `UNAUTHORIZED` | the session is missing or revoked |
| `RATE_LIMIT` | too many requests |
| `INVALID_PAYLOAD` | the payload failed validation (some rooms use their own code, named in the room section) |
| `SERVER_ERROR` | an unexpected failure, logged on the server |
| `ECON_INSUFFICIENT_FUNDS` | not enough of a currency; `extra: { currencyId, need, have }` |
| `RUNE_CAPACITY_FULL`, `ROSTER_FULL` | a reward does not fit into the inventory; nothing is granted |

## Close codes

| Code | Meaning |
| --- | --- |
| `4401` | the session was revoked: go back to the login screen |
| `4101` | maintenance or a GM disconnect (the default code) |
| `1011` | the presence room could not register the connection |
| `4000`-`4010` | reserved by Colyseus |

## `auth` (anonymous)

Join options: none. Request **`auth`**, multiplexed by `type`.

| type | payload |
|---|---|
| `register` | `{ type, email, password (6..256), username? (3..32), deviceId?, userAgent? }` |
| `login` | `{ type, emailOrUsername, password, deviceId?, userAgent? }` |
| `guest` | `{ type, deviceId?, userAgent? }` |
| `refresh` | `{ type, userId, refreshToken, deviceId?, userAgent? }` |
| `logout` | `{ type, userId, refreshToken, deviceId? }` |
| `cancel_deletion` | `{ type, emailOrUsername (1..255), password (1..256), deviceId?, userAgent? }` |

Success (register/login/guest/refresh/cancel_deletion):

```json
{ "action": "login", "ok": true, "userId": "8f0c...", "username": "Guest-01234",
  "accessToken": "eyJ...", "refreshToken": "q2B...",
  "account": { "userId": "8f0c...", "username": "Guest-01234", "isGuest": true, "email": null,
               "createdAtUnix": 1759663200, "deletionScheduledAtUnix": null },
  "snapshot": { "nickname": "Guest-01234", "level": 1, "currentExp": 0, "iconId": "icon_1",
                "serverTimeUnix": 1759663200, "wallet": [WalletItem...],
                "mapProgress": [{ "regionId": "region_1", "stageId": "region_1_stage_1",
                                  "difficulty": "Easy", "clears": 3, "bestClearMs": 41000 }] } }
```

`account` (same shape as the [`account`](#account) room's `info`): `email` is `null` for guests;
`deletionScheduledAtUnix` is always `null` in auth successes (pending accounts can't log in, and `cancel_deletion`
clears it).

`logout` answers `{ "action": "logout", "ok": true }` in every case; the device is only signed out when `refreshToken`
is that device's token.

Errors have the shape `{ "action", "ok": false, "error", "extra"? }`: `AUTH_INVALID_PAYLOAD`, `AUTH_UNKNOWN_ACTION`,
`AUTH_EMAIL_OR_USERNAME_TAKEN`, `AUTH_INVALID_CREDENTIALS`, `AUTH_ACCOUNT_LOCKED`, `AUTH_BANNED`
(`extra: { reason, until }`), `AUTH_INVALID_REFRESH`, `AUTH_RATE_LIMIT`, `MAINTENANCE` (every type except `logout`
while the server is in maintenance), `ACCOUNT_DELETION_PENDING` (`extra: { scheduledAtUnix }`) and
`ACCOUNT_NOT_PENDING_DELETION`.

Each login issues a new session for that device and revokes the previous one. `refresh` rotates the refresh token and
issues a new access token for the same session (same `jti`): rooms already joined keep working, and the client uses
the new token for later joins. Access tokens are only checked when a room is joined, so the client renews an expired
one with `refresh` when a join is rejected (`onAuth failed`) and retries the join once.

Account deletion (see `request_deletion` in the [`account`](#account) room):

- `login` of an account scheduled for deletion verifies the password first (wrong password →
  `AUTH_INVALID_CREDENTIALS`, counted toward the lock as usual); only with the correct password it answers
  `{ "action": "login", "ok": false, "error": "ACCOUNT_DELETION_PENDING", "extra": { "scheduledAtUnix": 1762255200 } }`.
- `refresh` answers the same `ACCOUNT_DELETION_PENDING` (+ `extra.scheduledAtUnix`) when the token matches one of the
  account's unexpired tokens, even if it was revoked by the deletion request; any other unknown token is
  `AUTH_INVALID_REFRESH`.
- `cancel_deletion` is verified exactly like `login` (unknown user/wrong password → `AUTH_INVALID_CREDENTIALS`,
  lock → `AUTH_ACCOUNT_LOCKED`, ban → `AUTH_BANNED`). If no deletion is scheduled → `ACCOUNT_NOT_PENDING_DELETION`.
  Otherwise the schedule is cleared, credentials are issued and the answer is the login success shape with
  `"action": "cancel_deletion"`. Guests can't cancel (they have no password).

## `account`

Account management of the logged-in player. Join option `accessToken` (like `profile`). Request **`account`**,
multiplexed by `type`. Every response echoes `action`. The user and the device always
come from the access token (session), never from the payload.

| type | payload | success |
|---|---|---|
| `info` | `{ type }` | `{ action, ok, account: Account }` |
| `link_email` | `{ type, email (valid email, ≤255), password (6..256) }` | `{ action, ok, account: Account }` |
| `change_password` | `{ type, currentPassword (1..256), newPassword (6..256) }` | `{ action, ok, revokedDevices }` |
| `logout_other_devices` | `{ type }` | `{ action, ok, revokedDevices }` |
| `request_deletion` | `{ type, confirm: "DELETE", password? (1..256) }` | `{ action, ok, deletionScheduledAtUnix, graceDays }` |

```jsonc
// Account (also the `account` object of auth successes)
{ "userId": "8f0c...", "username": "Guest-01234", "isGuest": false, "email": "bob@example.com",
  "createdAtUnix": 1759663200, "deletionScheduledAtUnix": null }   // email: null for guests
```

- `link_email`: guests only (`ACCOUNT_NOT_GUEST` otherwise). The email must not be used by another account as email
  or username (`AUTH_EMAIL_OR_USERNAME_TAKEN`). Sets the email and the password (Argon2id + pepper, like register),
  the account stops being a guest. The current session and refresh token stay valid; the player can now log in with
  email (or username) + password.
- `change_password`: guests get `ACCOUNT_IS_GUEST`. Wrong `currentPassword` → `ACCOUNT_WRONG_PASSWORD` and it counts
  toward the login lock (6 failures lock for 30 s → `AUTH_ACCOUNT_LOCKED`). `newPassword` equal to the current one →
  `ACCOUNT_SAME_PASSWORD`. On success the refresh tokens and sessions of **every other device** are revoked (they get
  `UNAUTHORIZED` / close code 4401 and must log in again); the calling device keeps its session and refresh token.
  `revokedDevices` = number of other devices logged out.
- `logout_other_devices`: same revocation of every other device, no password needed.
- `request_deletion`: `confirm` must be the literal `"DELETE"`. Registered accounts must send their correct
  `password` (missing or wrong → `ACCOUNT_WRONG_PASSWORD`; wrong ones count toward the lock); guests may omit it.
  Schedules the hard delete at now + `ACCOUNT_DELETION_GRACE_DAYS` (server setting, default 30; `graceDays` in the
  reply) and revokes every refresh token. Right **after** the reply, every session of the account is deleted,
  including the caller's: the client should show the confirmation and go back to the login screen (other rooms
  answer `UNAUTHORIZED`, presence closes with 4401). A repeated request keeps the original date. During the grace
  period `login`/`refresh` answer `ACCOUNT_DELETION_PENDING` and the player can undo it with `auth` →
  `cancel_deletion`. When the date passes, a daily job deletes the account and all its data permanently. With a
  0-day grace the account is deleted right after the reply.

```json
{ "action": "request_deletion", "ok": true, "deletionScheduledAtUnix": 1762255200, "graceDays": 30 }
```

Errors (`{ action, ok:false, error, extra? }`, `action` is `"unknown"` for unknown types): `INVALID_PAYLOAD`
(validation, unknown type or fields), `RATE_LIMIT`, `UNAUTHORIZED`, `ACCOUNT_NOT_GUEST`,
`AUTH_EMAIL_OR_USERNAME_TAKEN`, `ACCOUNT_IS_GUEST`, `ACCOUNT_WRONG_PASSWORD`, `ACCOUNT_SAME_PASSWORD`,
`AUTH_ACCOUNT_LOCKED`, `SERVER_ERROR`.
Rate limits per user: `info` uses the query limiter (60 / 10 s); every other type the dedicated account limiter
(5 / 30 s, burst 5).

Request **`economy`**, multiplexed by `type`. Every response echoes `action`.

| type | payload | success |
|---|---|---|

## `roster`

Invalid payload code: `ROSTER_INVALID_PAYLOAD`.

| request | payload | success |
|---|---|---|
| `list` | `{ offset?, limit? (1..500) }` | `{ ok, total, items: [ServerCharDTO+createdAtIso], nextOffset }` (BAG) |
| `storage_list` | `{ location?: "BAG"\|"STORAGE", offset?, limit? }` | `{ ok, storage: [...], total }` |
| `storage_caps` | `{}` | `{ ok, bagCapacity, storageCapacity, bagCount, storageCount }` |
| `storage_move` | `{ target: "BAG"\|"STORAGE", uids: [1..500] }` | `{ ok, target, moved, movedUids, bagCapacity, storageCapacity, bagCount, storageCount }` |
| `power_up` | `{ targetUid, fodderUids: [1..100], requestId? }` | `{ ok, targetUid, currencyId, priceSpent, expAdded, levelsGained, newLevel, newCurrentExp, removedFodders, skillUps: [{ skillIndex, skillId, level }], skillLevels }` |
| `evolve` | `{ targetUid, fodderUids: [1..100], requestId? }` | `{ ok, targetUid, newStars, resetLevelTo: 1, resetExpTo: 0, starPointsSpent, currencyId, priceSpent, removedFodders }` |
| `lock` | `{ uid, locked: bool }` | `{ ok, uid, locked }` |
| `sell` | `{ uids: [1..100], requestId? }` | `{ ok, soldUids, currencyId, amount, wallet }` |
| `expand` | `{ target: "BAG"\|"STORAGE", requestId? }` | `{ ok, target, bagCapacity, storageCapacity, currencyId, priceSpent, wallet }` |

Errors: `ROSTER_WRONG_LOCATION`, `ROSTER_CAPACITY_FULL` (`extra.target`), `ROSTER_CHARACTER_NOT_FOUND`,
`ROSTER_CHARACTER_LOCKED`, `ROSTER_AT_MAX_LEVEL`, `ROSTER_FODDER_NOT_FOUND`, `ROSTER_CANNOT_CONSUME_TARGET`,
`ROSTER_FODDER_HAS_RUNES`, `ROSTER_INSUFFICIENT_STAR_POINTS`, `ROSTER_EVOLVE_STEP_MISSING` (no
configured step / already 6★), `ROSTER_IN_DEFENSE`, `ROSTER_CAPACITY_MAX`, `ECON_INSUFFICIENT_FUNDS`.

Lock / sell / slots: roster entries carry `locked`. Locked monsters cannot be consumed (power-up / evolve fodder) or
sold, but can still be powered up / evolved themselves. Monsters of the arena defense cannot be consumed or sold
(`ROSTER_IN_DEFENSE`). `sell` pays `priceByStars[stars] + pricePerLevel x (level - 1)` each (`config.json >
gameplay.monsterSell`) and refuses runes still equipped (`ROSTER_FODDER_HAS_RUNES`). `expand` buys `step` slots for
`costBase + costIncrement x purchases so far` (`gameplay.capacityExpansion.bag|storage`, up to
`playerCapacity.max*Capacity`, else `ROSTER_CAPACITY_MAX`).

Power-up EXP: each fodder gives `baseExp` of its star tier plus its accumulated EXP (at least to `minFodderBaseLevel`)
x `factor` (`config.json > gameplay.powerUp.expMultiplierByStars: [{ stars, factor, baseExp }]`).

Skill-ups (`power_up`): every fodder that is the same `characterId` as the target or a skill-up material
(`characters.json` `skillUpMaterial`, Unity `CharacterData.SkillUpMaterial`, e.g. the Devilkin `devilkin_dark`) levels up one random skill
that is not at its `maxSkillLevel` (one `skillUps` entry each). A max-level target is accepted when at least one
skill-up can happen (`ROSTER_AT_MAX_LEVEL` otherwise). Skill levels drive cooldowns (`cooldownByLevel`) and the
cumulative `levelBonuses` (`damagePct`, `healPct`, `effectChancePct`) applied to every effect of the skill in battle.

## `awaken`

Request **`awaken`** `{ characterUid, preview?: bool, requestId? }` (`requestId` is ignored by previews).

- Success: `{ ok: true, instance: ServerCharDTO, walletAfter: {changed}, wallet: {full}, consumed: [{ currencyId, amount }] }`
- Preview that meets every requirement: `{ ok: true, preview: true, needs: [{ currencyId, need, have, missing }] }`
- Errors (fields at top level): `INVALID_REQUEST`, `CHAR_NOT_FOUND`, `CATALOG_NOT_FOUND`, `NO_MORE_AWAKENINGS`,
  `REQUIREMENT_LEVEL` (`requiredLevel, hasLevel`), `REQUIREMENT_STARS` (`requiredStars, hasStars`),
  `INSUFFICIENT_CURRENCY` (`missing: [{ currencyId, need, have, missing }]`); all except `INVALID_REQUEST` (invalid
  payload) carry `preview`.

## `rune`

Join option `accessToken`. Invalid payload code: `RUNE_INVALID_PAYLOAD`. Rune `quality` on the wire is
1 (Normal) … 5 (Legendary); the Unity `RuneQuality` enum is `quality - 1`.

| request | payload | success |
|---|---|---|
| `runes/search` | `{ setId?, slot?, qMin?, qMax?, lMin?, lMax?, equipped?, equippedTo?, lastId?, pageSize? (1..200) }` | `{ ok, items: [RuneSearchItem] }` |
| `runes/counts` | `{}` | `{ ok, items: [{ setId, freeCount }] }` |
| `runes/equip` | `{ runeUid, characterUid }` | `{ ok }` (replaces the rune in that slot) |
| `runes/unequip` | `{ characterUid, slot (1..6) }` | `{ ok }` |
| `runes/upgrade` | `{ runeUid, requestId? }` | `{ ok, success, rune: ServerRuneDTO, spend, currencyId, wallet, walletAfter }` |
| `runes/sell` | `{ runeUid }` | `{ ok, removedUid, currencyId, gained, wallet, walletAfter }` |
| `runes/delete` | `{ runeUid }` | `{ ok, removedUid }` (no refund) |
| `runes/lock` | `{ runeUid, locked: bool }` | `{ ok, runeUid, locked }` |
| `runes/favorite` | `{ runeUid, favorite: bool }` | `{ ok, runeUid, favorite }` |
| `runes/grant` | `{ setId, slot, tier, variant, quality (1..5), level?, mainStatType?, origin? }` | `{ ok, uid, rune }`; only with `DEV_TOOLS=true`, otherwise `FORBIDDEN` |

`RuneSearchItem` = `ServerRuneDTO` + `{ id, equippedAt, createdAt }`: `{ id, uid, setId, slot, tier, variant, quality,
level, mainStatType, mainStatValue, substats, origin, locked, favorite, equippedToUid, equippedAt, createdAt }`.
Use `lastId` = last item `id` for paging. `ServerRuneDTO` (upgrade, grants, rewards, shop) also carries `locked` and
`favorite` as 0/1. In the answers of `runes/upgrade` and `runes/sell`, `wallet` is the full wallet and `walletAfter` a
number: the new balance of `currencyId` (`null` after an upgrade that cost nothing).

Rules:
- **Lock** protects a rune: `runes/sell` and `runes/delete` answer `RUNE_LOCKED`. A locked rune can still be equipped,
  unequipped and upgraded. `lock`/`favorite` are idempotent and answer `RUNE_NOT_FOUND` for unknown or foreign runes.
- **Favorite** is display only (clients list favorites first); it never blocks an action.
- `runes/delete` runs the same checks as `sell`, in this order: `RUNE_NOT_FOUND`, `RUNE_LOCKED`,
  `RUNE_ALREADY_EQUIPPED` (unequip first). `RUNE_DELETE_FAILED` only if the row vanished concurrently.
- `runes/counts` = unequipped runes per set (locked ones included; sets without free runes are omitted), cached
  5 minutes and invalidated by every inventory change.

Errors: `RUNE_NOT_FOUND`, `RUNE_LOCKED`, `RUNE_ALREADY_EQUIPPED`, `RUNE_AT_MAX_LEVEL`, `RUNE_DELETE_FAILED`,
`RUNE_CAPACITY_FULL`, `ROSTER_CHARACTER_NOT_FOUND`, `ECON_INSUFFICIENT_FUNDS`.

## `summon`

Request **`summon`** `{ scrollId, times?: 1|10 (default 1), target?: "BAG"|"STORAGE" (default BAG), requestId? }` — `times: 10`
is the multi summon (grants the scroll's `multiGive` units for `tenPlusOneCost`; Unity `MultiSummonCount`, 11 = "10+1" by default).

- Success: `{ ok, scrollId, currencyId, spent, walletAfter: {currency: balance}, wallet: {full}, target,
  grants: [{ uid, characterId, stars, level, exp, currentExp, awakened, skillLevels, awakeningIndex }] }`
- Errors (`target` at top level when relevant): `INVALID_REQUEST` (also: multi summon on a scroll without
  10+1 offer), `SCROLL_NOT_FOUND`, `SCROLL_NOT_AVAILABLE` (banner scroll outside its window), `ROSTER_FULL`,
  `NOT_ENOUGH_SCROLLS`, `EMPTY_POOL`, `CHAR_NOT_IN_CATALOG`, `INVALID_WEIGHT_LIST`.

`summons.json` scrolls (Unity `SummonScrollDefinition`): `{ id, currencyId, costPerSummon, tenPlusOneCost, multiGive,
pools: [{ id, weight, minStars, maxStars, entries: [{ characterId, weight, rateUp }] }], availableFromUnix,
availableUntilUnix }`. A pool is picked by weight, then an entry by weight; the monster gets its natural stars. The
exporter writes only the entries the scroll can roll (natural stars inside the scroll and pool star range, element in
`AllowedElements`) and `weight` is the effective weight (Rate Up multiplier applied), so the server rolls what the
Offline backend rolls (sample Scroll of Light & Darkness `light_dark_scroll`: the only source of Light / Dark monsters,
pools 3★ 93.5% / 4★ 6% / 5★ 0.5%); `availableFromUnix` / `availableUntilUnix` (0 = open-ended) limit when it can be used (server clock).

Tutorial guaranteed summons (`config.json > tutorial > guaranteedSummons: [{ scrollId, characterIds: [] }]`, Unity
`TutorialDefinition`): the first summons of an account with that scroll grant those monsters in order (natural stars)
instead of rolling, a multi summon included; then the pools roll as usual. The count per scroll is kept in
`user_summon_counters` and only moves when a summon succeeds.

## `map`

Join option `accessToken`. State `MapState { int32 serverTimeUnix }`. The errors of `stage/validateStart` use
`{ ok: false, code, message }` (codes below); the other requests of this room (`map/progress`, `dungeon/status`,
`tower/status`) use the common `{ ok: false, error }`.

**`stage/validateStart`** `{ regionId, stageId, difficulty: "Easy"|"Normal"|"Hard"|"Hell", uidsInSlots (max 10 strings), leaderSlotIndex, requestId? }`
(an empty list answers `NO_UNITS`, more units than the stage formation holds `FORMATION_TOO_LARGE`). The request
checks unlocks, formation and ownership, pays the energy and issues a battle ticket.

```json
{ "ok": true, "sceneName": "region_1_region_1_stage_1", "currencyId": "EN", "energySpent": 1,
  "wallet": { "EN": 9, "GO": 1000 }, "ticketId": "01J..." }
```

Codes: `INVALID_PAYLOAD`, `INVALID_CREDENTIALS`, `STAGE_NOT_FOUND`, `STAGE_SCENE_MISSING` (the stage has no `scene` in `maps.json`), `REGION_NOT_FOUND`, `DIFFICULTY_LOCKED`,
`REGION_LOCKED`, `STAGE_LOCKED`, `INVALID_STAGE_FORMATION`, `NO_UNITS`, `FORMATION_TOO_LARGE`,
`INVALID_LEADER_SLOT`, `DUPLICATE_UNITS`, `UNIT_NOT_OWNED`, `INSUFFICIENT_FUNDS`, `DUNGEON_CLOSED`,
`DUNGEON_LEVEL_LOCKED`.

**`map/progress`** `{}` → `{ ok, stages: [{ regionId, stageId, difficulty, clears, bestClearMs }] }`.

### Stage rewards and drop tables (farming)

`maps.json` stage rewards are per difficulty: `{ difficulty, currencies, firstClearCurrencies, unitExp, accountExp,
dropTableId, randomDrops }`. `dropTableId` references a shared table of `maps.json > dropTables` (exported from the
Unity `StageDropTable` assets) so that stages can be farmed:

```jsonc
{ "id": "drops_story_r3_hard",
  "rune": { "chance": 0.42,                                   // one rune per victory at most
            "stars": [{ "stars": 3, "weight": 35 }, { "stars": 4, "weight": 50 }, { "stars": 5, "weight": 15 }],
            "grades": [{ "grade": 1, "weight": 24 }, { "grade": 2, "weight": 34 }, { "grade": 3, "weight": 26 },
                       { "grade": 4, "weight": 13 }, { "grade": 5, "weight": 3 }],   // 1 Normal .. 5 Legend
            "sets": [] },                                       // empty = any set
  "items": [{ "currencyId": "magic_mid", "min": 1, "max": 1, "chance": 0.09 }] }   // independent rolls
```

Every victory rolls, in this order (the Unity offline backend mirrors it, `OfflineStageDrops`): the table's `items`,
the stage's own `randomDrops` (extra rolls of that stage, e.g. hall essences), then the rune (`chance`, then stars
and grade by weight, then the set). The rune is generated with that grade (initial substats by grade); a full rune
inventory skips it. Unknown `dropTableId`s are ignored with a warning; a table without star weights never drops
runes. Rolled items are added to the result `currencies`; the rune is in `runes` (with `quality`).

### Dungeons (elemental halls)

Regions with `kind: "dungeon"` in `maps.json` are dungeon halls: their stages are the floors (B1..B10), only
`Easy` exists, each floor unlocks when the previous floor was cleared and they are not part of the story chain
(story regions unlock one after another ignoring halls). `dungeons.json` (exported from the Unity
`DungeonDefinition`) lists the halls with `openDays` (0 = Sunday .. 6 = Saturday, evaluated after
`resetHourUtc`) and `minAccountLevel`; `stage/validateStart` refuses closed halls (`DUNGEON_CLOSED`) and low
accounts (`DUNGEON_LEVEL_LOCKED`) before paying. Hall floors usually keep their essences as `randomDrops`
(`[{ currencyId, min, max, chance }]`, rolled independently on every victory) and reference a drop table for the rest
(rune dungeons: a table with a few rune `sets`, see "Stage rewards and drop tables").

**`dungeon/status`** `{}` →
`{ ok, serverTimeUnix, resetHourUtc, nextResetAtUnix, halls: [{ regionId, kind: "essence"|"rune"|"special", elementId, openDays, open, minAccountLevel, levelLocked }] }`
(server time is authoritative for the open state).

### Towers (Spire of Trials)

Regions with `kind: "tower"` are towers: their stages are the floors, only `Easy` exists and they are not part of the
story chain. `towers.json` (exported from the Unity `TowerDefinition`): `{ towers: [{ regionId, reset:
"monthly"|"weekly"|"never", resetHourUtc, weekStartsOn, minAccountLevel }] }`. Floors are climbed in order once per
season (`user_tower_progress`, season keys `M:2026-10` / `W:2026-10-05` / `all`): `stage/validateStart` refuses
`TOWER_LEVEL_LOCKED`, `TOWER_FLOOR_LOCKED` (not the next floor) and `TOWER_FLOOR_CLEARED` (already cleared this
season). A won floor advances the season and its `firstClearCurrencies` are granted again every season (`firstClear`
in the battle result follows the season). Floors may cost 0 energy.

**`tower/status`** `{}` →
`{ ok, serverTimeUnix, towers: [{ regionId, reset, seasonKey, clearedFloors, totalFloors, minAccountLevel, levelLocked, resetsAtUnix }] }`
(`resetsAtUnix` 0 = never resets).

Clears are recorded when the server-side battle is won; there is no request to report one.

## `battle_pve`

Join option `accessToken`. One player per room, one battle at a time: the client opens a room for each battle and
leaves it after the result (a retry opens a new one). Invalid payload code: `INVALID_REQUEST`. Errors:
`{ ok:false, requestId, error, message?, ...fields }`.

| request | payload | notes |
|---|---|---|
| `battle_start` | `{ regionId, stageId, difficulty, uidsInSlots, leaderSlotIndex, requestId?, ticketId? }` | starts a stage battle |
| `battle_start_arena` | `{ opponentId, uidsInSlots, leaderSlotIndex, requestId? }` | a PvP arena attack, see [`arena`](#arena) |
| `battle_command` | `{ requestId?, battleId?, actorId, skillId, targetId }` | skill levels come from the roster; in TeamPhase `actorId` may be any unit of `actorOptions` |
| `battle_auto` | `{ requestId?, battleId? }` | the AI plays the current player unit |
| `battle_surrender` | `{ requestId?, battleId? }` | ends the battle as a defeat |
| `battle_result` | `{ requestId?, battleId? }` | the result of a finished battle (idempotent) |
| `battle_state` | `{ requestId?, battleId? }` | the current frame after a reconnection, with `snapshot: true` |

The stage enemies (every wave, levels and stats with the difficulty scaling) are resolved by the server at
`battle_start` and arrive in the frame `state`.

`battle_start` requires a ticket from `stage/validateStart` (newest unused one for that stage/difficulty
in the last `gameplay.stageStartTicketMinutes` minutes of `config.json` (default 30), or the given `ticketId`), otherwise
`STAGE_NOT_VALIDATED`. Other errors: `UNIT_NOT_OWNED`, `NO_UNITS`, `FORMATION_TOO_LARGE`,
`INVALID_LEADER_SLOT`, `DUPLICATE_UNITS`, `INVALID_STAGE_FORMATION`, `STAGE_NOT_FOUND`, `NO_ENEMY_WAVES`,
`CHAR_NOT_FOUND`, `BATTLE_IN_PROGRESS`. The ticket is checked before the
battle is built (a player without a ticket gets `STAGE_NOT_VALIDATED` first); only one start can be in flight per room, a
concurrent `battle_start` / `battle_start_arena` answers `BATTLE_IN_PROGRESS` and consumes nothing.

**One live battle per player.** A player holds one running battle across rooms, devices and server processes (entries
in the Colyseus presence). A start while another room holds a running battle answers `BATTLE_IN_PROGRESS` with
`activeBattle: { roomId, battleId, mode, sinceUnix }` (`mode` `pve` | `arena` | `pvp`) so the client can resume it;
`activeBattle` is absent when the other start is still in flight. The slot is freed by the final frame, by leaving the
room and when the room closes; an entry whose room no longer exists (crashed process) is ignored and cleared.

**Reconnection.** A connection lost while the battle runs (not a `leave()`) keeps the seat for
`social.json > battleRooms.reconnectSeconds` (default 45 s; 0 = off). Nothing advances meanwhile. The client reconnects
with the room's reconnection token (`client.reconnect(token)`) and asks `battle_state`: its frame is the last step (with
`actionOptions`), the events of that step were already played or lost with the old connection, so the client rebuilds
the scene from `state` instead of replaying `events`. When the window expires, or the player leaves on purpose, the
battle is abandoned: PvE grants nothing (the ticket stays spent), an arena battle is settled as a defeat. After an app
restart the client finds the battle with the presence request `battle_active`.

Command errors: `BATTLE_NOT_STARTED`, `BATTLE_ID_MISMATCH` (the `battleId` must be the room's battle),
`BATTLE_ALREADY_FINISHED`, `BATTLE_NOT_FINISHED` (`battle_result` before the end), plus engine
rejections as a frame with `ok:false` and `error` (e.g. `INVALID_PLAYER_ACTOR`, `NOT_AWAITING_PLAYER_INPUT`,
`SKILL_ON_COOLDOWN`, `INVALID_TARGET`, `ACTOR_NOT_READY`); a rejected frame still carries the unchanged state and
options.

Frame (answer of start, command, auto and surrender). Every frame has the same fields:

```jsonc
{ "ok": true, "requestId": "c12", "error": null,
  "battleId": "01J...",
  "phase": "awaiting_action",        // "waiting_for_turn" | "awaiting_action" | "finished" ...
  "turn": 7, "round": 3,
  "finished": false,
  "victory": null,                   // true/false once finished (draws and surrender are false)
  "winnerSideId": null,              // "players" | "enemies" | null
  "finishedReason": null,            // "elimination" | "surrender" | "turn_limit" | "draw"
  "awaitingPlayerInput": true, "activeUnitId": "player-1", "activeSideId": "players",
  "currentWaveIndex": 0, "totalWaves": 2,
  "actionOptions": {                 // null unless the server waits for the player
    "actorId": "player-1",
    "forcedTargetId": null,          // provoker id: only skill 1 on this target is accepted
    "skills": [{ "skillId": "fire_slash", "usable": true, "reason": null, "cooldown": 0,
                 "targetSide": "enemies", "targetIds": ["enemy-1", "enemy-2"] },
               { "skillId": "inferno", "usable": false, "reason": "SKILL_ON_COOLDOWN", "cooldown": 2,
                 "targetSide": "enemies", "targetIds": [] }] },
  "actorOptions": null,              // TeamPhase while the player picks a unit: one actionOptions per ready unit
  "turnOrder": {                     // upcoming actors of the configured turn order system
    "mode": "AttackBar",             // "AttackBar" | "SpeedRounds" | "AlternatingSides" | "TeamPhase"
    "round": 3, "sideId": null,      // AlternatingSides: side of the next slot; TeamPhase: side of the phase
    "actorIds": ["player-1", "enemy-2", "player-3"],
    "nextActorIds": [] },            // round modes: predicted order of the next round (TeamPhase: next phase)
  "state": { /* full BattleState: units (with metadata.row/slotIndex), teams, statuses... (see docs/BATTLE_EVENTS.md) */ },
  "events": [ /* events produced by this step, in order (docs/BATTLE_EVENTS.md) */ ],
  // only on the final frame (finished == true):
  "result": { "victory": true, "firstClear": true,
              "currencies": [{ "currencyId": "GO", "amount": 300 }],
              "units": [{ "uid": "01J...", "characterId": "knight_fire", "expGained": 250, "level": 12,
                          "currentExp": 340, "leveledUp": true }],
              "runes": [ServerRuneDTO],
              "account": { "expGained": 30, "level": 8, "currentExp": 120, "expToNext": 410, "levelsGained": 1,
                           "rewards": [{ "currencyId": "EN", "amount": 42 }] },
              "wallet": { "GO": 12345 } } }
```

`account` (the player's account EXP): the stage's `accountExp`, else energy spent x `gameplay.accountExp.expPerEnergy`
(`config.json`, exported from Unity `GameInstance.AccountProgression`). Every reached level credits its
`levelUpRewards` and tops `refillOnLevelUp` currencies (energy) up to the new cap; `rewards` lists both.
EXP past `maxLevel` is discarded (`expToNext` 0).

Turn order systems (combat config `turnOrder.mode`, docs/BATTLE_RULES.md "Turn order"): in `TeamPhase` the server
stops before the player's units act with `phase: "waiting_for_turn"`, `awaitingPlayerInput: true`,
`activeUnitId: null`, `actorOptions` (every ready player unit that can act, AI order) and `actionOptions` = the first
of them. `battle_command` with any of those `actorId`s starts that unit's turn and uses the skill in the same frame
(an already used unit is refused with `ACTOR_NOT_READY`); `battle_auto` plays the first one.

Rewards are granted only when the session reports `victory: true`. Defeat/surrender/draw:
`"result": { "victory": false }`. If settling failed the final frame has `result: null` and
`resultError`; call `battle_result` to retry (rewards are granted once per battle).

Battle setup (server side): player units keep the slot index they had in `uidsInSlots` (empty slots are `""`),
`metadata.row` is `Frontline` for slots `< formation.front`, otherwise `Backline`; the leader is the unit in
`leaderSlotIndex`; each battle uses a random RNG seed (`state.metadata.seed`) and the stage's optional
`turnLimit` (`state.metadata.turnLimit`). Leader skills are applied to the stats when the battle is created;
`AllEnemies` / `AllUnits` scopes also reach the opposing side (enemy bonuses that target the player come from the
first wave); a leader `modeFilter` (`arena`, `dungeon`, `tower`) is matched against the battle's content mode
(`state.metadata.contentMode`: the stage region kind `story` / `dungeon` / `tower`, or `arena`). Passive auras are
evaluated live by the battle engine (docs/BATTLE_RULES.md "Passives"). Skill levels are stored per skill slot: an
awakening replacement (`rewards.replaceSkills`) keeps the slot and its level.

## `home`

Request **`home`**, multiplexed by `type`. Invalid payload: `HOME_INVALID_PAYLOAD`.

| type | payload | success |
|---|---|---|
| `get_snapshot` | `{ type }` | `{ action, ok, snapshot }` |
| `place_object` | `{ type, islandId, definitionId, originX, originZ, yawDegrees? }` | `{ action, ok, snapshot, wallet }` |
| `move_object` | `{ type, islandId, instanceId, originX, originZ, yawDegrees? }` | `{ action, ok, snapshot }` |
| `remove_object` | `{ type, islandId, instanceId }` | `{ action, ok, snapshot, wallet }` |
| `unlock_island` | `{ type, islandId }` | `{ action, ok, snapshot, wallet }` |
| `collect_production` | `{ type, islandId, instanceId }` | `{ action, ok, snapshot, wallet, collected, units }` |
| `set_production_units` | `{ type, islandId, instanceId, uids }` | `{ action, ok, snapshot, units }` |

`snapshot = { selectedIslandId, revision, serverTimeUnix, islands: [{ islandId, unlocked, revision,
removedTemplateInstanceIds, placements: [{ instanceId, templateInstanceId, buildableId, x, z, yawDegrees,
isTemplateObject, production? }] }], inventory: [{ buildableId, count }] }`. `revision` is a monotonic counter bumped by
every mutation. `inventory` lists the unplaced buildings the player owns (granted by `shop/purchase`
`grants.constructions`; only entries with `count > 0`). `wallet` in the `place_object`, `remove_object` and
`unlock_island` replies is the player's full wallet after the debit: clients replace their cached wallet with it
(Unity: `BackendClientSync.ApplyWalletSnapshot`) and never charge locally. The Unity offline backend
(`OfflineHomeService`) applies the same rules.

Placing and removing:

- `place_object` consumes one unit of `definitionId` from the inventory when the player has one: no `placeCost` is
  charged and the buildable may have `canPurchase: false` (shop-exclusive buildings). Without stock the buildable must
  have `canPurchase: true` and its `placeCost` is debited (`HOME_NOT_PURCHASABLE` otherwise). Unlock level, footprint,
  bounds, overlap and the unique and `maxCount` limits are validated in both cases, in the same transaction; a rejected
  placement consumes nothing.
- `remove_object` charges the buildable's remove cost (`removeCostCurrencyId` / `removeCostAmount` of `homes.json`) in
  the same transaction as the removal, for player objects and island template objects alike, after the `canRemove`
  check (`HOME_NOT_REMOVABLE` charges nothing). A blank currency id or an amount `<= 0` is free; without funds it
  fails with `ECON_INSUFFICIENT_FUNDS` and nothing changes. The building is destroyed and not returned to the
  inventory; use `move_object` to reposition.
- Footprints: `homes.json` carries one cell list per 90° rotation (`footprints[rotationIndex]`, offsets from the origin
  cell); the one nearest to the normalized yaw is validated. Rotations turn clockwise seen from above (+Z towards +X,
  the direction of a positive Unity yaw) around the origin cell, so a 2x1 building becomes 1x2.

Islands:

- `homes.json` `islands[]` carry `unlockedByDefault`, `unlockLevel`, `unlockCostCurrencyId`, `unlockCostAmount` and
  `order` (exported from each Unity `HomeIslandAuthoring`). The player starts with the default islands; every other
  island is bought with `unlock_island`. The payload is only `{ type, islandId }`: the price and the level always come
  from `homes.json`.
- `unlock_island` checks, in this order: unknown island (`HOME_ISLAND_NOT_FOUND`); default or already owned island
  (`HOME_ISLAND_ALREADY_UNLOCKED`); account level below `unlockLevel` (`HOME_LOCKED`). Then it claims the ownership row
  of `user_home_islands` (unique `(user, island)`) and debits the price in the same transaction (a blank currency id or
  an amount `<= 0` is free; `ECON_INSUFFICIENT_FUNDS` rolls the claim back). A repeated or concurrent purchase of the
  same island waits on the unique key and answers `HOME_ISLAND_ALREADY_UNLOCKED` without a second debit. On success
  the island becomes `selectedIslandId` and the snapshot shows it `unlocked: true`.
- `place_object`, `move_object` and `remove_object` on an island with `unlocked: false` fail with `HOME_ISLAND_LOCKED`
  and charge nothing.

Errors: `HOME_ISLAND_NOT_FOUND`, `HOME_ISLAND_LOCKED`, `HOME_ISLAND_ALREADY_UNLOCKED`, `HOME_DEFINITION_NOT_FOUND`,
`HOME_OBJECT_NOT_FOUND`, `HOME_NOT_PURCHASABLE`, `HOME_NOT_MOVEABLE`, `HOME_NOT_REMOVABLE`, `HOME_LOCKED`,
`HOME_LIMIT_REACHED`, `HOME_INVALID_FOOTPRINT`, `HOME_OUT_OF_BOUNDS`, `HOME_CELL_BLOCKED`, `HOME_OVERLAP`, the
production codes below, and `ECON_INSUFFICIENT_FUNDS`.

### Production buildings

A buildable in `homes.json` may carry a `production` block (exported from the Unity `BuildableConfig`); without it the
building produces nothing.

```json
"production": { "kind": "currency", "currencyId": "DM", "amountPerHour": 1, "capacity": 12, "unitSlots": 0 }
```

- `kind` `"currency"`: stores `amountPerHour` units of `currencyId` per hour up to `capacity`; collecting credits the wallet.
- `kind` `"unitExp"` (training grounds): the player stations up to `unitSlots` (1..10) monsters; each accrues
  `amountPerHour` EXP per hour up to `capacity` EXP; collecting gives the stored EXP to every stationed monster.
- A block is **active** only when the kind is known, `amountPerHour > 0`, `capacity > 0`, a currency producer has a
  non-blank `currencyId` and a unit EXP producer has `unitSlots >= 1`. Malformed or inactive blocks are treated as absent
  (the building shows no `production` and every production request answers `HOME_NO_PRODUCTION`).

State per placed producing object (player objects and island template objects alike; keyed by `instanceId`, which is the
`templateInstanceId` for template objects) is persisted in `user_home_production`: `sinceUnix` (integer seconds, the
accrual anchor) and `units` (stationed roster uids; they may name monsters sold or fed since, which are ignored when
collecting and dropped from the list on the next write). **No stored row means `sinceUnix = 0` and `units = []`**: a
default building of an island (the main island Crystal Tower) starts full. `place_object` of a producing buildable
stores a row with `sinceUnix = now` (a new building starts empty), `remove_object` deletes the row and `move_object`
keeps it.

Every placement of a producing buildable carries `production: { sinceUnix, units }` in the snapshot (absent for the other
placements). Clients compute the live counter with the formula below and `snapshot.serverTimeUnix`; they never grant
anything themselves.

Formula (integer math, identical in the Unity `HomeProductionRules`):

```
elapsed = max(0, now - sinceUnix)
stored  = min(capacity, floor(elapsed * amountPerHour / 3600))
```

After `stored` was collected the anchor moves to:

```
if stored >= capacity: sinceUnix' = now
else:                  sinceUnix' = min(now, sinceUnix + ceil(stored * 3600 / amountPerHour))
```

so the partial progress toward the next unit is kept and a full building restarts from now. For `unitExp`, `stored` is the
EXP **each** stationed monster receives.

**`collect_production`** `{ type, islandId, instanceId }` - checks, in order: island exists (`HOME_ISLAND_NOT_FOUND`),
unlocked (`HOME_ISLAND_LOCKED`), placement exists (`HOME_OBJECT_NOT_FOUND`), active production block
(`HOME_NO_PRODUCTION`). In one transaction (rows locked, `now` from the server clock):

- currency: `stored < 1` gives `HOME_NOTHING_TO_COLLECT`; otherwise `stored` units of `currencyId` are credited.
- unitExp: the stationed monsters that still exist are locked (scoped by the player); none, or `stored < 1`, gives
  `HOME_NOTHING_TO_COLLECT`; otherwise each one receives `stored` EXP with the battle EXP rules (`applyExp`: level ups,
  clamp at the max level of its stars) and the building `units` is rewritten without the missing uids.
- the new anchor is stored and the home `revision` is bumped.

Reply `{ action: "collect_production", ok: true, snapshot, wallet, collected, units }`: `wallet` is the full wallet after
the credit (like `place_object`); `collected = { currencyId, amount }` for a currency producer, `null` for a unit EXP
producer; `units = [{ uid, characterId, expGained, level, currentExp, leveledUp }]` (the battle `UnitRewardDto`; `expGained`
is the EXP actually consumed, `0` at max level), `[]` for a currency producer.

**`set_production_units`** `{ type, islandId, instanceId, uids }` - `uids`: 0..10 roster uids, each 1..80 chars, all
distinct (otherwise `HOME_INVALID_PAYLOAD`). After the same island/lock/object checks and `HOME_NO_PRODUCTION` (also for
a currency producer): `uids.length > unitSlots` gives `HOME_PRODUCTION_SLOTS_FULL`; a uid the player does not own gives
`HOME_UNIT_NOT_FOUND`; a uid stationed in **another** production building of the player gives `HOME_UNIT_BUSY`
(rearranging the monsters of the same building is allowed). In one transaction the EXP pending on the **current**
monsters is settled first (like a collect when `stored >= 1` and any of them exist; nothing pending is not an error),
then `units = uids` and `sinceUnix = now` are stored and the `revision` is bumped.

Reply `{ action: "set_production_units", ok: true, snapshot, units }`: `units` is the EXP settled on the previous monsters
(same shape as above, `[]` when nothing was pending).

Production error codes: `HOME_NO_PRODUCTION`, `HOME_NOTHING_TO_COLLECT`, `HOME_PRODUCTION_SLOTS_FULL`,
`HOME_UNIT_NOT_FOUND`, `HOME_UNIT_BUSY`.

## `shop`

Join option `accessToken`.

**`shop/state`** `{}` →

```json
{ "ok": true, "serverTimeUnix": 1759831200,
  "counters": [{ "itemId": "daily_gold", "windowKey": "D:2026-10-06", "count": 1 },
               { "itemId": "starter_hero", "windowKey": "U", "count": 0 }],
  "firstPurchased": ["daily_gold"], "iapDemo": false }
```

`iapDemo` = real-money items are granted without payment (demo purchases on, see below).
`counters` has one entry per limited item (scope ≠ None or unique) with the count of its **current**
window. Window keys (UTC; `resetHourUtc` is the UTC reset hour, weeks start on `weekStartsOn`,
0 = Sunday): `D:YYYY-MM-DD` (day start), `W:YYYY-MM-DD` (week start date), `M:YYYY-MM`, `U`
(lifetime/per account/no window). Treat keys as opaque.

**`shop/purchase`** `{ itemId, expectedPrice?: { currencyId, amount }, purchaseId?: string (8..64), receipt? }`

```json
{ "ok": true, "itemId": "daily_gold", "currencyId": "gem", "priceSpent": 5,
  "wallet": { "gem": 95, "gold": 2500 },
  "grants": { "currencies": [{ "currencyId": "gold", "amount": 1500 }], "characters": [ServerCharDTO], "runes": [ServerRuneDTO],
             "constructions": [{ "buildableId": "hut", "count": 2 }] },
  "counter": { "itemId": "daily_gold", "windowKey": "D:2026-10-06", "count": 1 },
  "firstPurchaseBonusGranted": true }
```

- `expectedPrice` different from the server price → `PRICE_CHANGED` with `price: { currencyId, amount }`.
- `purchaseId` is an idempotency key: retries with the same id return the first response (nothing is granted twice).
- `grants.constructions` = buildings added to the player's inventory (merged per `buildableId` across rewards and
  first-purchase bonus); place them with `home` `place_object`. `forceUnique` caps the grant at 1 unit and requires
  that the player owns none yet (inventory + placed, island template defaults included); otherwise the purchase is
  rejected with `SHOP_ALREADY_OWNED` (`extra.buildableId`) **before** anything is charged or any receipt validated
  (rejecting is safer than skipping the grant, which would still take the price or a real-money receipt).
  A `buildableId` missing from the home catalog answers `SHOP_REWARD_NOT_SUPPORTED` (`extra.rewards: ["construction:<id>"]`).
- Errors (`{ ok:false, error, itemId, extra? }`): `SHOP_ITEM_NOT_FOUND`, `SHOP_NOT_AVAILABLE`,
  `SHOP_NOT_ELIGIBLE` (`extra.requirement`), `SHOP_LIMIT_REACHED`, `PRICE_CHANGED`, `SHOP_REWARD_NOT_SUPPORTED` (custom
  payloads, unknown buildables), `SHOP_ALREADY_OWNED` (`forceUnique` building), `ECON_INSUFFICIENT_FUNDS`, `ROSTER_FULL`,
  `RUNE_CAPACITY_FULL`, and the real-money errors below.

### Real-money items (`RealMoneyIAP`, docs/IAP.md)

**`shop/iap_check`** `{ itemId }` → `{ ok, itemId, productId, demo, accountToken }`. Asked **before** the store payment
opens: runs every check of `shop/purchase` (availability, eligibility, limits, `forceUnique` buildings) without
charging. `productId` = store product of the item's current price; `demo` = send a `Demo` receipt instead of paying;
`accountToken` = UUID derived from the account, passed to the store (Apple `appAccountToken`, Google
`obfuscatedAccountId`) so the server can check who bought the receipt. A currency-priced item answers
`IAP_NOT_SUPPORTED` (`extra.detail: "NOT_REAL_MONEY"`).

**`shop/purchase`** with `receipt` (required for a real-money price; on a currency price it is refused with
`IAP_PRODUCT_MISMATCH`, `extra.detail: "NOT_REAL_MONEY"`):

```json
{ "itemId": "shop_item_diamond_001",
  "receipt": { "store": "GooglePlay", "productId": "diamond_pack_1", "purchaseToken": "<token>", "transactionId": "GPA.1234-5678" } }
{ "itemId": "shop_item_diamond_001",
  "receipt": { "store": "AppleAppStore", "productId": "diamond_pack_1", "transactionId": "2000000123456789", "signedTransaction": "<StoreKit 2 JWS>" } }
{ "itemId": "shop_item_diamond_001",
  "receipt": { "store": "Demo", "productId": "diamond_pack_1", "transactionId": "<random id per purchase>" } }
```

- The server verifies the receipt with the store **before** its transaction (Google Play: Android Publisher API with
  the service account, acknowledged after the grant; App Store: StoreKit 2 signed transaction against Apple's root
  certificate; Demo: accepted only while demo purchases are on), then grants like any purchase (`priceSpent: 0`,
  `currencyId: null`).
- Each store transaction is delivered once across all accounts (`user_iap_transactions`; `Demo` receipts are scoped to
  the account). The same receipt sent again by the same account answers the first response (the client retries until it
  can finish the store transaction); from another account it answers `IAP_RECEIPT_USED`. The client-sent `purchaseId`
  is ignored for receipts.
- A verified payment is delivered even if the offer window closed meanwhile; limits still apply.
- Errors: `IAP_NOT_SUPPORTED` (no receipt, unknown store, store not set up: `extra.detail` e.g.
  `GOOGLE_PLAY_NOT_CONFIGURED`, `APP_STORE_NOT_CONFIGURED`, `UNKNOWN_STORE`), `IAP_RECEIPT_REJECTED` (`extra.detail`:
  `UNKNOWN_PURCHASE`, `CANCELLED`, `REFUNDED`, `INVALID_SIGNATURE`, `TEST_PURCHASE`, `ACCOUNT_MISMATCH`,
  `MULTI_QUANTITY_NOT_SUPPORTED`, `UNSUPPORTED_PRODUCT_TYPE`, ...), `IAP_RECEIPT_USED`, `IAP_PRODUCT_MISMATCH`,
  `IAP_DEMO_DISABLED`, `IAP_PURCHASE_PENDING` (payment still pending at the store) and `IAP_STORE_UNAVAILABLE`
  (store unreachable or server credentials refused: retry later; the client keeps the order unfinished).

## `mail`

The player's mailbox. Join option `accessToken`. Mails carry optional rewards (shop payload shape:
`currencies`, `scrolls`, `characters`, `runes`, `constructions`) granted once when claimed. Settings come from
`mail.json` (exported from the Unity `MailDefinition`; defaults: inbox of 100, mails expire after 30 days, a welcome
mail with `DM` 100 + `GO` 20000).

| request | payload | answer |
|---|---|---|
| `mail/list` | `{}` | inbox |
| `mail/summary` | `{}` | `{ ok, unread, claimable }` (menu badge) |
| `mail/read` | `{ mailIds: string[] }` | inbox |
| `mail/claim` | `{ mailId }` | inbox + claim fields |
| `mail/claimAll` | `{}` | inbox + claim fields |
| `mail/delete` | `{ mailIds: string[] }` | inbox |
| `mail/deleteRead` | `{}` | inbox (deletes read mails without unclaimed rewards) |

Inbox →

```jsonc
{ "ok": true, "serverTime": "…", "unread": 2, "claimable": 1, "inboxLimit": 100,
  "mails": [{ "mailId": "a1b2c3d4e5f60718", "category": "reward",      // system | guild | reward | gm
              "sender": "Arena Council", "title": "Welcome, Summoner!", "body": "…",
              "titleKey": "text_mail_welcome_title", "bodyKey": "text_mail_welcome_body", "params": [],
              "attachments": { "currencies": [{ "currencyId": "DM", "amount": 100 }], "scrolls": [], "characters": [],
                               "runes": [], "constructions": [] },   // empty = plain message
              "createdAt": "…", "expiresAt": "…" /* or null */, "read": false, "claimed": false }] }  // newest first
```

Claim fields: `claimedIds`, `grants` (`{ currencies, characters, runes, constructions }`), `wallet`, `stoppedBy`.
`claimAll` claims oldest first, one transaction per mail; when a mail does not fit (e.g. `RUNE_CAPACITY_FULL`) the
rest stay unclaimed and `stoppedBy` names the error (failing on the first mail answers that error instead).

Texts: show `titleKey`/`bodyKey` translated with `params` substituted into `{0}`, `{1}`…; fall back to `title`/`body`.

`list` and `summary` first deliver the welcome mail (once per account) and pending broadcasts; `list` also drops
expired mails (`summary` only leaves them out of its counts). A mail with unclaimed rewards cannot be deleted
(`MAIL_HAS_REWARDS` for a single delete; batches skip it) until it expires, and it is never trimmed when the inbox
overflows (the oldest read mails and expired mails are). Push: `presence` → `mail_new`, after which the client asks
`mail/summary`.

Errors: `MAIL_NOT_FOUND`, `MAIL_EXPIRED`, `MAIL_ALREADY_CLAIMED`, `MAIL_NOTHING_TO_CLAIM`, `MAIL_HAS_REWARDS`,
`RUNE_CAPACITY_FULL` / `ROSTER_FULL`.

Operators send mail with `POST /admin/runtime/mail/send` (see [GM panel API](#gm-panel-api-http)) or in the GM panel,
"Mail" tab. Broadcasts are stored once and copied into each inbox when the player next opens it (accounts created later
only with `includeNewPlayers`).

## `story`

Dialogue/tutorial progress. Join option `accessToken`. The client owns the dialogue content (text, portraits,
tutorial steps, triggers); the server stores what the player completed and grants the rewards of `dialogues.json`
(exported from the Unity `DialogueSequenceDatabase`: `{ allowUnknownDialogues, dialogues: [{ id, prerequisites,
minAccountLevel, requiredStageClear, repeatable, rewardWhenSkipped, rewards }] }`, `rewards` = shop payload shape;
`requiredStageClear` = stage id of a sequence triggered by `stage_clear:<stageId>`, else null). Without the file any
well-formed id can be completed (no prerequisites, no rewards).

| request | payload | answer |
|---|---|---|
| `story/state` | `{}` | state |
| `story/progress` | `{ dialogueId, step }` | state (remembers the sequence in progress to resume it) |
| `story/clear` | `{}` | state (forgets the sequence in progress) |
| `story/complete` | `{ dialogueId, skipped?: bool }` | state + `{ dialogueId, firstTime, grants, wallet }` (`wallet` is `null` when nothing was granted) |

State → `{ ok, serverTime, completed: [{ dialogueId, skipped, times, completedAt }], active: { dialogueId, step } | null }`.

`complete` checks `prerequisites` (all completed), `minAccountLevel` and `requiredStageClear` (that stage won at least
once, any difficulty), then grants `rewards` on the first completion
(not when `skipped` and `rewardWhenSkipped` is false). Completing again is accepted without rewards (`firstTime:
false`); repeatable sequences count `times`. Errors: `STORY_LOCKED` (`requires` | `requiredLevel` | `requiredStage`),
`STORY_UNKNOWN_DIALOGUE` (with `allowUnknownDialogues: false`, or once the account already completed 200 ids that are not
in the catalog; catalog ids are unlimited), `RUNE_CAPACITY_FULL` / `ROSTER_FULL`.

## `ranking`

Leaderboards, read only. Join option `accessToken`. The categories come from `ranking.json` (exported from the Unity
`RankingDefinition`; defaults: the six categories below). Every category is computed from existing tables; its top list
is cached (in the server process and in the shared cache) for `refreshSeconds` and reused by every request, so the heavy
queries do not run per request. The caller's own row is a bounded lookup computed on every request. Banned players are
left out. Requests use the `query` rate limit.

| request | payload | answer |
|---|---|---|
| `ranking/categories` | `{}` | `{ ok, defaultLimit, categories: [{ id, kind, subject, order, titleKey, descriptionKey, valueKey, iconId, topSize, refreshSeconds }] }` (enabled ones, ascending `order`; `[]` when rankings are disabled) |
| `ranking/list` | `{ category, limit? }` | `{ ok, category, subject, updatedAtUnix, nextRefreshUnix, entries, me }` |

`limit` is 1..100, default `defaultTopSize` of the config, and never more than the category's `topSize`.
`entries[]` (best first; equal values share the rank, 1-1-3):

```jsonc
{ "rank": 1, "displayName": "Bizachi", "iconId": "icon_1", "level": 42, "value": 1530,
  "guildTag": "Quest Testers" /* null without a guild; always null in guild categories */, "isMe": false }
```

`me` is the caller's own row with the same fields plus `inTop` (the caller is inside the cached list). `me.rank` 0 =
not ranked (nothing to rank yet: no arena profile, no tower floor...). In guild categories `me` is the caller's guild
(`null` without a guild). Internal user and guild ids are never sent.

Categories (`kind`; `subject` is `player` except for guilds, whose `level` field is the member count):

| kind | ranks | value |
|---|---|---|
| `level` | account level, then experience (equal level and exp share a rank) | account level |
| `arena` | `arena_profiles.rating` (the arena ranking) | rating |
| `tower` | floors cleared in the **current season** of each tower (`user_tower_progress`, all towers added up, or only `regionId`) | floors |
| `story` | stages cleared (`user_stage_progress.clears > 0`) in the campaign regions (dungeons and towers excluded), each weighted by its difficulty (`difficultyWeights`, default Easy 1, Normal 2, Hard 3, Hell 4) | points |
| `collection` | distinct `characterId`s owned (bag + storage) | monsters |
| `guild` | guild activity points of the current guild week (`guild_activity`, same week as the guild quests) | points |

Config entry: `{ id, kind, enabled, order, titleKey, descriptionKey, valueKey, iconId, topSize (0 = default),
refreshSeconds (0 = default), regionId (tower), difficultyWeights (story) }`; file fields `enabled`, `defaultTopSize`
(50), `defaultRefreshSeconds` (120). `valueKey` is a translation key with `{0}` = the value. A cached list is dropped as
soon as its metric changes (tower season or guild week rollover, config change).

Errors: `RANKING_DISABLED`, `RANKING_UNKNOWN_CATEGORY` (unknown or disabled `category`), `RATE_LIMIT`, `INVALID_PAYLOAD`.

### Player reports (`report_player`)

The reporter is always the session user.

- **`report_player`** `{ targetUserId?, category, comment? (≤ 300), messageId?, source }` → `{ ok: true, reportId }`
  or `{ ok: false, error }`.
  - `category`: `spam` | `offensive` | `cheating` | `name` | `other` (restricted by `config.json > reports > categories`).
  - `source`: `global_chat` | `guild_chat` | `private_chat` | `profile` | `arena` | `friends` | `other`.
  - `messageId`: the `id` of a `chat` line (`source: "global_chat"`), of a `guild_chat` line (`source: "guild_chat"`)
    or of a private message the reporter received (`source: "private_chat"`).
    The server copies that line and the target's latest stored chat lines into the report itself; text sent by the
    client is never used (the payload has no text fields besides `comment`). With a `messageId` the sender of the
    line is the target, so `targetUserId` may be omitted (guild chat lines carry no user ids); when both are given
    they must agree. Guild lines are only reportable by members of that guild.
  - Rules: no self reports; the target must exist; one open report per reporter → target (a new one is possible
    once a GM handled it); a cooldown between two reports and a rolling 24 h limit per reporter. Rate limited like
    the other account actions (`RATE_LIMIT`).
  - Errors: `REPORTS_DISABLED`, `REPORT_CATEGORY_INVALID`, `REPORT_SELF`, `REPORT_TARGET_NOT_FOUND`,
    `REPORT_MESSAGE_NOT_FOUND` (unknown line, not the target's, or a guild line of another guild), `REPORT_DUPLICATE`,
    `REPORT_COOLDOWN` (`retryAfterSeconds`), `REPORT_LIMIT` (`dailyLimit`), `INVALID_PAYLOAD`, `RATE_LIMIT`.
- Feedback: when a GM resolves the report with an action the reporter gets a system mail (`category: system`, keys
  `text_mail_report_handled_title` / `text_mail_report_handled_body`, receipt `report:<id>`) and `mail_new`.

`config.json > reports` (absent = defaults):

| key | default | notes |
|---|---|---|
| `enabled` | `true` | `false` → `REPORTS_DISABLED` |
| `dailyLimit` | `10` | reports per player per rolling 24 h (1..1000) |
| `cooldownSeconds` | `30` | minimum seconds between two reports of a player (0..86400) |
| `categories` | all five | subset of the categories the server accepts |
| `historyLines` | `5` | stored chat lines of the target copied into the report (0..20) |
| `notifyReporter` | `true` | mail the reporter when a GM resolves the report with an action |

## `chat_directory` (anonymous)

Request **`list`** `{}` → `{ ok, suggestedChannel, currentPool, maxPool, channels: [{ channel, players }], serverTimeUnix }`
Push **`channels_update`** `{ channel, players, serverTimeUnix }`.

`channels` lists the default pool (`0 .. initialPool-1`, empty ones included) plus every other channel that has players;
channels nobody is in are not listed beyond the default pool. `suggestedChannel` is the emptiest channel below
`recommendedPerChannel`; when all of them are full it is the next channel of the pool (up to `maxPool`), and
`currentPool` always covers the suggested channel and every listed one (`<= maxPool`).

## `chat`

Join options `{ channel: int, accessToken }` (rooms are filtered by `channel` and `listOnly`);
`{ listOnly: true }` joins an anonymous helper that only answers `list` like `chat_directory`.
`channel` must be an integer in `0 .. maxPool-1` (`maxPool` = `max(initialPool, maxPool)` of `config.json > chat >
directory`): a missing, fractional, negative or non-numeric value is channel `0`, a channel `>= maxPool` is refused at
join time (no room is created). A channel is counted (directory `players`) from the moment a player joined it, not when
its room is created. An anonymous (`listOnly`) client that reaches a real channel room is refused at join; only the
helper rooms are anonymous. `history` has the per-user query limit (`RATE_LIMIT`).

- **`history`** `{ limit? (1..200) }` → `{ ok, channel, messages: [ChatMessage], serverTimeUnix, muteUntilUnix }`
- **`send`** `{ message }` → `{ ok, serverTimeUnix }` or `{ ok:false, error: "RATE_LIMIT"|"MUTED"|"INVALID"|"MESSAGE_BLOCKED", muteUntilUnix?, serverTimeUnix }`
  (`MESSAGE_BLOCKED`: the word filter is in `block` mode and the text contains a banned word; nothing is stored or
  delivered. In `mask` mode the line is accepted and every client receives the masked text.)
- Push **`chat_msg`** `ChatMessage` to everyone in the channel.

`ChatMessage` = `{ id?, userId, nickname, iconId, level, channel, message, original?, serverTimeUnix }`:

| field | type | notes |
|---|---|---|
| `id` | int | stored line id (`chat_messages.id`); what `report_player` names in `messageId` (`presence`). Optional: lines that were not stored carry none |
| `userId` | string | sender account id |
| `nickname` | string | sender display name at send time (`"Player"` if the profile could not be read) |
| `iconId` | string \| null | sender's selected profile icon at send time (`user_profile.icon_id`, empty -> `icons.json` default). `null` when the profile could not be read: show a default avatar |
| `level` | int (>= 1) | sender's account level at send time (`user_profile.level`) |
| `channel` | int | channel number |
| `message` | string | sanitized text; masked by the word filter when it matched (what clients show by default) |
| `original` | string | the unmasked sanitized text. Present only when the line was masked AND `chat.filter.allowPlayerOptOut` is true; absent on clean lines and when the opt-out is off. Same on `chat_msg`, `history` and the sender's own echo. See "Word filter" |
| `serverTimeUnix` | int | send time (history: stored `created_at`) |

`nickname`, `iconId` and `level` are snapshotted into `chat_messages` when the message is sent, so history shows the
sender as they were at that moment (later icon/level changes do not rewrite old messages).

### Word filter

One filter (`ChatService.moderate`) serves `chat` and `guild_chat`; nicknames (`profile`) and guild name / description /
notice (`guild`) use it in `block` mode only. Exported from Unity as `config.json > chat > filter`
(absent = disabled):

| key | default | notes |
|---|---|---|
| `enabled` | `false` | master switch (also off while `words` is empty) |
| `mode` | `"mask"` | `mask`: matched characters of the original text become `maskChar` (separators and spaces inside a spaced-out word included); `block`: the message is refused with `MESSAGE_BLOCKED`, nicknames and guild texts with `TEXT_BLOCKED` |
| `maskChar` | `"*"` | first character is used |
| `words` | `[]` | single words (max 5000, 64 characters each; one-letter entries are ignored) |
| `allowList` | `[]` | words that are never flagged: a banned match lying inside an allow-listed word is dropped |
| `wholeWordOnly` | `true` | `true`: a banned word must be a whole word (no "Scunthorpe" problem); `false`: also inside longer words. Words in Chinese, Japanese or Korean script always match anywhere (no word boundaries) |
| `allowPlayerOptOut` | `true` | `mask` mode only: masked lines also carry the unmasked text as `original` (`chat` and `guild_chat` messages: live, history and the sender's echo) so a player can turn the filter off for themselves. `false`: `original` is never sent. Ignored in `block` mode (nothing is delivered) |
| `bundledLists` | all | server-only word lists merged into `words` (`wordlists/`, LDNOOBW CC-BY 4.0 minus `exclude/` plus `extra/`): any of `en`, `pt`, `ja`, `ko`, `zh`; `[]` turns them off |

Matching ignores case, accents, repeated letters, leetspeak (`0 1 3 4 5 7 @ $`; `1`/`l`/`i` are interchangeable) and
separators (`. - _ * | ~ ^` inside a word, spaces between single letters: `f.u.c.k`, `f u c k`). Not caught by design:
`*` used as a wildcard (`f*ck`), phrases with spaces, homoglyphs beyond accents. The algorithm is documented in
`src/modules/chat/chat-filter.ts` and its cases are in `test/fixtures/chat-filter-cases.json`. The filter is server
only: the Unity offline backend does not filter chat, and the bundled lists never ship with the Unity package.
In `mask` mode the server stores both texts (`message` masked, nullable `original_message` only on masked lines) and
sends `message` always plus `original` when `allowPlayerOptOut` is on. The client decides what to show through a
local setting (e.g. "Show unfiltered chat", stored on the device, off by default): off = `message`, on =
`original ?? message`. The server has no per-player setting and never needs to know it. `report_player` evidence
(reported line and context lines in `player_reports`) and the GM panel chat views always use the original text (the
panel marks masked lines); `allowPlayerOptOut: false` only stops sending `original` to players.
The GM panel (Chat > Word filter) shows masked / blocked counters per player since the server started and a test box.

## `guild_chat`

The player's guild channel. Join option `accessToken` (any logged-in player may join; there is one shared
room type, no channel option). The channel is decided on the server from `guild_members` on join, on every `history`
and `send`, and by the guild events: players only ever receive their own guild's lines, and leaving, being kicked or
the guild being disbanded removes access immediately (joining/being accepted grants it without reconnecting).
Messages go through the same moderation as `chat` (per-IP token bucket, mutes shared with the global channels,
sanitizing, `msgMin`/`msgMax`, per-user window, duplicate mute) and the newest 80 lines per guild are kept
(`guild_chat_messages`, deleted with the guild).

- **`history`** `{ limit? (1..200) }` → `{ ok, guildId, guildName, messages: [GuildChatMessage], serverTimeUnix, muteUntilUnix }`;
  without a guild `{ ok: false, error: "GUILD_NOT_MEMBER", guildId: null, guildName: null, messages: [], serverTimeUnix }`.
- **`send`** `{ message }` → `{ ok, serverTimeUnix }` or `{ ok: false, error: "GUILD_NOT_MEMBER"|"RATE_LIMIT"|"MUTED"|"INVALID"|"MESSAGE_BLOCKED", muteUntilUnix?, serverTimeUnix }`
  (a per-user request limit answers `RATE_LIMIT` before anything else; membership is checked before the moderation; `MESSAGE_BLOCKED` and the masking are the chat word filter, see `chat`).
  The line `id` is also what `report_player` takes as `messageId` with `source: "guild_chat"`.
- Push **`guild_chat_msg`** `GuildChatMessage` to the members of that guild connected to `guild_chat`.
- Push **`guild_chat_state`** `{ inGuild, guildId, guildName, serverTimeUnix }` right after joining the room and
  whenever the player's guild changes (created, joined, accepted, left, kicked, disbanded by the leader or by a GM).
  Access is revoked even if posting the system line fails.

`GuildChatMessage` = `{ id, kind, nickname, iconId, level, message, original?, system?, self, serverTimeUnix }`:

| field | type | notes |
|---|---|---|
| `id` | int | increasing line id (dedupe history vs pushes) |
| `kind` | `"user"` \| `"system"` | system lines are guild events |
| `nickname` | string | sender name at send time; system lines: the player the line is about |
| `iconId` | string \| null | sender's profile icon at send time (`null` on system lines) |
| `level` | int (>= 1) | sender's account level at send time |
| `message` | string | sanitized text, masked by the word filter when it matched; system lines: English text (`"Bob joined the guild."`) |
| `original` | string | unmasked text; same rule as `ChatMessage.original` (only on masked user lines while `chat.filter.allowPlayerOptOut` is true; live push and `history`; never on system lines) |
| `system` | string | system lines only: `created`, `joined`, `left`, `kicked`, `promoted`, `demoted`, `leader` (client key `text_guild_chat_sys_<system>`, `{0}` = `nickname`) |
| `self` | bool | the recipient sent the line (internal user ids are never sent) |
| `serverTimeUnix` | int | send time |

System lines are posted after the guild change commits: `created` (guild founded), `joined` (open join or accepted
request), `left`, `kicked`, `promoted` / `demoted` (officer role), `leader` (transfer). A leader leaving alone
disbands the guild without a line. Changes made by the account purge job post no line.

## `guild`

Guilds (one per player). Join option `accessToken`. Invalid payload code `INVALID_PAYLOAD`. Limits, emblems,
tags and the creation cost come from `guild.json` (exported from the Unity `GuildDefinition`; built-in defaults:
names 3-20 chars, 30 members, 3 officers, 3 tags, 3 pending requests per player expiring after 48 h, creation
`GO` 10000 at account level 3+). Members are identified by a public `memberId` handle; internal user ids are never sent.

| request | payload | who |
|---|---|---|
| `guild/state` | `{}` | anyone |
| `guild/list` | `{ query?: string }` (empty = recommended) | anyone |
| `guild/details` | `{ guildId }` | anyone |
| `guild/checkName` | `{ name }` | anyone |
| `guild/create` | `{ name, description?, iconId, tags?, joinType?: "open"\|"approval", minLevel? }` | no guild |
| `guild/join` | `{ guildId }` | no guild |
| `guild/cancelRequest` | `{ guildId }` | applicant |
| `guild/leave` | `{}` | member |
| `guild/requests` | `{}` | leader, officer |
| `guild/acceptRequest` / `guild/rejectRequest` | `{ requestId }` | leader, officer |
| `guild/kick` | `{ memberId }` | leader (anyone), officer (members only) |
| `guild/setRole` | `{ memberId, role: "officer"\|"member" }` | leader |
| `guild/transfer` | `{ memberId }` | leader |
| `guild/update` | `{ description?, notice?, iconId?, tags?, joinType?, minLevel? }` (only the given fields) | leader, officer |
| `guild/quests` | `{}` | member |
| `guild/claimQuest` | `{ questId }` | member |
| `guild/claimChest` | `{ chestId }` | member |

**`guild/state`** (also the response of `create`, `join`, `cancelRequest`, `leave`, `acceptRequest`, `rejectRequest`,
`kick`, `setRole`, `transfer` and `update`) →

```jsonc
{ "ok": true, "serverTime": "2026-10-11T12:00:00.000Z",
  "guild": { "guildId": "…uuid…", "name": "Dragon Knights", "description": "…", "notice": "…" /* own guild only */,
             "iconId": "emblem_lion", "tags": ["casual"], "joinType": "open", "minLevel": 1,
             "memberCount": 12, "maxMembers": 30, "leaderName": "Bob", "createdAt": "…" },   // null without a guild
  "role": "leader",                                   // "leader" | "officer" | "member" | null
  "members": [{ "memberId": "9f2c41d07a6b3e58", "name": "Bob", "level": 30, "iconId": "icon_1", "role": "leader",
                "joinedAt": "…", "lastActiveAt": "…" /* or null */, "online": true, "self": true }],
  "requestCount": 2,                                  // pending requests (leader/officers, else 0)
  "myRequests": [{ "guildId": "…", "name": "Moon Order", "iconId": "emblem_moon", "memberCount": 8, "maxMembers": 30,
                   "createdAt": "…", "expiresAt": "…" }] }   // only without a guild
```

Extra fields: `create` → `wallet` (balances after paying `creationCost`); `join` → `joined` / `requested`;
`leave` → `disbanded` (the leader left alone, the guild is deleted).

**`guild/list`** → `{ ok, guilds: [GuildView + { requested }] }`, up to 30. With `query`: case-insensitive name
substring. Without: guilds with room first, then those whose `minLevel` you meet, open ones, most members, newest.
**`guild/details`** → `{ ok, guild (no notice), members: [{ name, level, iconId, role, online }], requested }`.
**`guild/checkName`** → `{ ok, name (normalized), available, reason? }` (`reason` = `GUILD_NAME_INVALID` or
`GUILD_NAME_TAKEN`). **`guild/requests`** → `{ ok, requests: [{ requestId, name, level, iconId, createdAt, expiresAt }] }`.

Rules: names are trimmed, inner spaces collapsed, need a letter or digit, refuse control characters, `<`, `>` and the
configured forbidden characters, are capitalized per word (`autoCapitalizeName`) and unique case-insensitively.
Descriptions/notices drop control characters (single newlines kept) and `<`/`>` unless rich text is allowed.
`open` guilds are joined instantly; `approval` guilds create a request (removed when accepted, rejected, cancelled,
expired, or when the player joins any guild). Officers kick plain members only; the leader promotes/demotes (up to
`maxOfficers`) and transfers the lead (the old leader becomes officer, member when officers are full). The leader must
transfer before leaving unless alone (then the guild is disbanded). When an account is purged, a leader is replaced
by the longest-serving officer (else member) and empty guilds are deleted.

Guild notices: players affected by someone else's decision get a mail (category `guild`, sender = guild name,
`titleKey`/`bodyKey` = `text_mail_guild_<notice>_title|body`, `params: [guildName]`) committed with the change:
`accepted`, `rejected`, `kicked`, `promoted`, `demoted`, `leader` (transfer or succession after a purge).

### Guild quests

Configured in `guild.json` → `quests` (`enabled`, `resetHourUtc`, `weekStartsOn` (0 = Sunday), `daily: [{ id, kind,
target, guildPoints, rewards }]`, `chests: [{ id, points, rewards }]`; `rewards` = shop payload shape). Built-in
defaults: 5 daily quests (5 stage clears, 3 arena battles, 1 summon, 3 rune upgrades, 1 power-up) and 4 chests
(300 / 800 / 1500 / 3000 points).

- Kinds: `stage_clear` (PvE victory), `arena_battle` (any settled arena battle), `summon` (per monster summoned),
  `rune_upgrade` (per upgrade attempt; selling a rune does not count), `monster_powerup` (per power-up; an evolve
  counts as one too). Counted only while the player is in a guild, after
  the action committed, capped at the quest's `target`; progress is per player and resets every day.
- `guild/claimQuest` (progress ≥ target, once per day) grants `rewards` and adds `guildPoints` to the player's guild
  for the current week.
- `guild/claimChest`: once per player per week when the guild's week points reach `points` (claims are per player,
  so changing guilds never allows a second claim).

**`guild/quests`** →

```jsonc
{ "ok": true, "serverTime": "…", "dayKey": "D:2026-10-11", "weekKey": "W:2026-10-05",
  "dailyResetAt": "2026-10-12T00:00:00.000Z", "weeklyResetAt": "2026-10-12T00:00:00.000Z",
  "quests": [{ "questId": "daily_stage_clear", "kind": "stage_clear", "target": 5, "progress": 3, "claimed": false,
               "guildPoints": 20, "rewards": { "currencies": [{ "currencyId": "GO", "amount": 5000 }], "runes": [], … } }],
  "guildPoints": 420,                     // guild total this week
  "myPoints": 60,                         // the player's contribution this week
  "chests": [{ "chestId": "chest_bronze", "points": 300, "rewards": { … }, "unlocked": true, "claimed": false }],
  "contributors": [{ "name": "Bob", "level": 30, "iconId": "icon_1", "points": 120, "self": false }] }  // top 10
```

`guild/claimQuest` / `guild/claimChest` answer the same state plus `grants` (`{ currencies, characters, runes,
constructions }`, like `shop/purchase`) and `wallet`.

Errors: `GUILD_NOT_FOUND`, `GUILD_NAME_TAKEN`, `GUILD_NAME_INVALID`, `GUILD_TEXT_TOO_LONG` (`max`),
`GUILD_INVALID_ICON`, `GUILD_INVALID_TAG`, `GUILD_ALREADY_MEMBER`, `GUILD_NOT_MEMBER`, `GUILD_NO_PERMISSION`,
`GUILD_FULL`, `GUILD_LEVEL_TOO_LOW` (`requiredLevel`), `GUILD_REQUEST_EXISTS`, `GUILD_REQUEST_LIMIT` (`limit`),
`GUILD_REQUEST_NOT_FOUND`, `GUILD_LEADER_MUST_TRANSFER`, `GUILD_OFFICER_LIMIT` (`limit`), `GUILD_INVALID_TARGET`,
`GUILD_QUESTS_DISABLED`, `GUILD_QUEST_NOT_FOUND` (unknown quest or chest id), `GUILD_QUEST_NOT_COMPLETE`,
`GUILD_QUEST_CLAIMED`, `GUILD_CHEST_LOCKED` (`points`), `GUILD_CHEST_CLAIMED`,
`TEXT_BLOCKED` (`create` name / description and `update` description / notice contain a word banned by the chat
word filter in `block` mode; GM edits skip it), `ECON_INSUFFICIENT_FUNDS` (`extra: { currencyId, need, have }`).

## `social`

Request room for friends, blocks, private messages and friendly battle challenges (the match itself runs in
[`battle_pvp`](#battle_pvp)). Join option `accessToken`. Pushes never come from this room: they reach every presence
connection of the player as **`social_event`** (see the table at the end), so the client may join `social` only while a
social screen is open. Tuning: `social.json` (Unity `SocialDefinition`, sections `friends`, `directMessages`,
`friendlyBattle`, `battleRooms`). Players are addressed by `targetUserId` (the user id the chat lines already carry) or,
for `friends/request`, by exact profile `name`.

`PlayerCardDto` (every list): `{ userId, name, iconId, level, status, lastSeenUnix, relation }` with `status`
`online` | `in_battle` | `offline` (online = a presence heartbeat within `friends.onlineWindowSeconds`, default 60 s;
in battle = a battle room holds the player's slot, also during a reconnection window), `lastSeenUnix` only when offline,
and `relation` `self` | `none` | `friend` | `pending_in` | `pending_out` | `blocked` (blocked = the viewer blocked them;
being blocked by someone is never shown).

### Friends (query bucket for reads, mutation bucket for writes)

| request | payload | answer |
|---|---|---|
| `friends/summary` | `{}` | `{ ok, incomingRequests, unreadMessages }` (menu badge) |
| `friends/list` | `{}` | `{ ok, friends: [PlayerCardDto + friendsSinceUnix + unread], maxFriends, incomingRequests }` (online first, then in battle, offline; by name) |
| `friends/requests` | `{}` | `{ ok, incoming: [FriendRequestDto], outgoing: [FriendRequestDto], maxPendingOutgoing }`; `FriendRequestDto` = `{ requestId, direction, createdAtUnix, player }` |
| `friends/search` | `{ query }` | `{ ok, players: [PlayerCardDto], minChars }`: names starting with `query` (case-insensitive, at least `searchMinChars`, at most `searchMaxResults`, shortest names first) |
| `friends/profile` | `{ targetUserId }` | `{ ok, player, guildName, arena: { rating, wins, losses } \| null, friendCount }` |
| `friends/request` | `{ targetUserId }` or `{ name }` | `{ ok, relation: "pending_out" \| "friend", requestId, player }`: a pending request from the target is accepted instead; asking again answers the same request |
| `friends/accept` / `friends/reject` | `{ requestId }` | `{ ok, friend }` / `{ ok }` (incoming requests only) |

### Private messages

Friends only (`directMessages.allowGuildMembers` also lets guild mates write to each other); a block either way stops
them. Text rules, rate limits, GM mutes and the word filter are the global chat ones (`config.json > chat`); the
`chatSend` bucket applies before any database work. Conversations keep their newest `historyPerConversation` lines.

| request | payload | answer |
|---|---|---|
| `dm/conversations` | `{}` | `{ ok, conversations: [{ peer, lastMessage, unread, lastAtUnix, canMessage }], unreadTotal }` (most recent first, at most `maxConversations`) |
| `dm/history` | `{ targetUserId, beforeId?, limit? }` | `{ ok, peer, messages: [DmMessageDto], hasMore, canMessage }`: the newest page (`historyPageSize`), `beforeId` pages back; oldest first in the page |
| `dm/send` | `{ targetUserId, message }` | `{ ok, serverTimeUnix, message: DmMessageDto }` or `{ ok: false, error, muteUntilUnix?, serverTimeUnix }` |
| `dm/read` | `{ targetUserId, upToId }` | `{ ok, unread, unreadTotal }` |

`DmMessageDto` = `{ id, self, message, original?, serverTimeUnix }` (`original` like the chat: unmasked text when the
word filter masked the line and the opt-out is allowed). `dm/send` errors: `DM_DISABLED`, `PLAYER_NOT_FOUND`,
`SOCIAL_SELF`, `DM_NOT_ALLOWED` (not friends / guild mates, or a block either way), then the chat moderation codes
`RATE_LIMIT`, `MUTED`, `INVALID`, `MESSAGE_BLOCKED`. Lines can be reported with `report_player`
(`source: "private_chat"`, `messageId`): only the recipient of the line may report it.

## `arena`

Asynchronous PvP (rules and rationale: `docs/ARENA.md`). Join option `accessToken`. Invalid payload code
`INVALID_PAYLOAD`. Opponents are **defense teams played by the battle AI**; the battle itself is served by the
`battle_pve` room (`battle_start_arena`), so the PvE battle presenter is reused. Formations have at most 4 slots
(`uidsInSlots.length <= 4`, `leaderSlotIndex` 0..3, empty slots are `""`; slots 0-1 are the front line).

| request | payload |
|---|---|
| `arena/state` | `{}` |
| `arena/setDefense` | `{ uidsInSlots, leaderSlotIndex }` |
| `arena/opponents` | `{ refresh?: bool }` |
| `arena/defenseLog` | `{}` |
| `arena/ranking` | `{}` |

**`arena/state`** → `{ ok, rating, wins, losses, defenseWins, defenseLosses, rank, defense, wings, season, seasonResult }`.
`rating` starts at 1000; `rank` = 1 + players with a higher rating; `defense` is `{ uidsInSlots, leaderSlotIndex }`
or `null`; `wings` = Arena Wing (`AW`) balance with recharge applied (max, interval and the `GP` currency are in
`currencies.json`).

Seasons (`arena.json` → `seasons`, rules in `docs/ARENA.md` "Seasons"; both fields are `null` when seasons are
disabled). An ended season is settled before the state is built: the tier rewards are **mailed** (category `reward`,
`titleKey` `text_mail_arena_season_title`, `bodyKey` `text_mail_arena_season_body`, `params` = `[season, tierName,
rating]`, claimed in the [`mail`](#mail) room) and the rating gets the soft reset, so `rating` is already the new
season's rating.

```jsonc
"season": { "number": 40,
            "startsAt": 1791158400000, "endsAt": 1791763200000,  // unix ms, endsAt exclusive
            "serverTime": 1791201600000,                         // unix ms (time left = endsAt - serverTime)
            "battles": 3, "minBattles": 1,                       // attacks this season / needed for the season reward
            "tierId": "challenger",                              // tier of the current rating
            "nextTierId": "fighter", "nextTierMinRating": 1250,  // null at the top tier
            "resetRating": 1078,                                 // rating the next season would start with
            "tiers": [{ "id": "beginner", "name": "Beginner", "minRating": 0,
                        "rewards": [{ "currencyId": "GP", "amount": 50 }, { "currencyId": "GO", "amount": 5000 }] }] },
"seasonResult": { "season": 39, "tierId": "fighter", "rating": 1310, "battles": 4,   // or null
                  "rewards": [{ "currencyId": "GP", "amount": 200 }], "ratingAfter": 1155,
                  "mailed": true, "settledAt": 1791158460000 }
```

`seasonResult` is the last ended season you fought in (at least `minBattles` attacks); it is returned by the **first**
`arena/state` after it was settled (whoever settled it: this request, a battle, or the server sweep), then `null`, so
the client can announce "Season 39 ended: you reached Fighter, rewards were sent to your mailbox". Players without an
attack in a season get no reward and no `seasonResult` (their rating is still reset). Tier names: translate
`text_arena_tier_<id>`, fall back to `name`.

**`arena/setDefense`** → `{ ok, defense }`. Units must be owned (`UNIT_NOT_OWNED`); formation errors:
`NO_UNITS`, `FORMATION_TOO_LARGE`, `INVALID_LEADER_SLOT`, `DUPLICATE_UNITS`. The defense is snapshotted from the
roster (runes included) **when an attack starts**; a player without defense is never offered.

**`arena/opponents`** →

```jsonc
{ "ok": true,
  "opponents": [{ "opponentId": "u:9f2c41d07a6b3e58" /* or "npc:npc_rookie" */, "name": "Bob", "rating": 1034, "level": 7,
                  "units": [{ "characterId": "knight_fire", "star": 2, "level": 12, "element": "fire_element" }] }],
  "refreshedAt": "2026-10-05T12:00:00.000Z",        // null until the first explicit refresh
  "nextFreeRefreshAt": "2026-10-05T12:10:00.000Z",
  "refreshCost": { "currencyId": "DM", "amount": 5 }, // null when early refresh is disabled
  "wallet": { "DM": 95 } }                            // only when the refresh was paid
```

Up to `opponentCount` entries (`arena.json`, default 6) sorted by rating: real players with a defense within the
first of `ratingWindows` (default ±200, widening to ±400, then any rating), excluding yourself and players you attacked
in the last `recentAttackHideSeconds` (default 600); the rest is filled with NPC rivals from `arena.json` closest in
rating. `opponentId` is a public handle (`u:<publicId>`): internal user ids, uids and rune
details are never sent. The list is cached until refreshed or until an attack consumes it (the next call builds a
new one for free). `refresh: true` is free when the last refresh is older than `freeRefreshSeconds` (default 600), otherwise it costs
`refreshCost` (`NOT_ENOUGH_CURRENCY`; `ARENA_REFRESH_NOT_AVAILABLE` when the config disables paid refreshes).

**`arena/defenseLog`** → `{ ok, entries: [{ attackerName, defenseWon, ratingChange, at }] }` — last `defenseLogSize` (default 20) finished
attacks on your defense, newest first (`ratingChange` is yours: negative when `defenseWon` is false; `at` ISO UTC).

**`arena/ranking`** → `{ ok, top: [{ rank, name, level, rating, self }], own: { rank, rating } }` — top `rankingSize` (default 100) by rating
(ties share the rank).

**`battle_start_arena`** (room `battle_pve`) `{ opponentId, uidsInSlots, leaderSlotIndex, requestId? }` → the same
first frame as `battle_start` (`state.mode == "arena"`, attacker side `players`, defender side `enemies` played by
the AI, single wave, `state.metadata.turnLimit` from `arena.json`, default 60). `battle_command`, `battle_auto`,
`battle_surrender` and `battle_result` work unchanged. `wingCost` Arena Wings (`arena.json`, default 1) are spent in
the transaction that creates the battle and are not refunded on defeat. Errors (frame with `ok:false`): `OPPONENT_NOT_OFFERED` (id not in your current list),
`NO_DEFENSE`, `NOT_ENOUGH_CURRENCY` (`extra: { currencyId, need, have }`), `BATTLE_IN_PROGRESS`, plus the
formation errors above (`UNIT_NOT_OWNED` for units that are not yours).

The final frame `result` replaces the PvE reward block (a draw by turn limit, surrender and leaving the room count
as defeat):

```jsonc
"result": { "victory": true,
            "currencies": [{ "currencyId": "GP", "amount": 10 }, { "currencyId": "GO", "amount": 2000 }],
            "arena": { "ratingBefore": 1000, "ratingAfter": 1016, "delta": 16 },
            "wallet": { "AW": 9, "GP": 10, "GO": 3000 } }
```

Rating (Elo, K = 32, floor 0): attacker `+delta` on a win and `-delta` on a loss, a real defender gets the mirror
change (clamped at 0), NPC rivals never change. Rewards (`arena.json`: default win `GP` 10 + `GO` 2000, loss `GP` 2)
and rating changes are applied once per battle id: `battle_result` replays the stored result.

## `battle_pvp`

One real-time friendly battle, created by the server when a challenge is accepted. A client cannot create it (the
creation needs a ticket only the server signs) and only the two players can join: `joinById(roomId, { accessToken })`.
A second connection of a player already in the match is refused (reconnect with the token instead). Both players hold
the battle in the live battle registry from the room's creation (`battle_active` answers `mode: "pvp"`).

Phases (push **`pvp_state`** after every change, also `pvp/state` on request):

```jsonc
{ "matchId": "01J...", "phase": "lobby",   // lobby | prepare | battle | finished
  "deadlineUnix": 1792364000,              // end of the lobby / prepare phase (null in battle)
  "battleId": null,
  "you":      { "userId": "...", "name": "Ann", "iconId": null, "level": 12, "sideId": "side_a", "ready": false, "connected": true },
  "opponent": { "userId": "...", "name": "Bob", "iconId": null, "level": 10, "sideId": "side_b", "ready": false, "connected": true },
  "result": null }                          // finished: { friendly: true, victory, winnerUserId, reason }
```

1. **lobby**: both players join within `friendlyBattle.joinTimeoutSeconds` (default 30), otherwise the match is aborted
   (`pvp_aborted { matchId, reason: "join_timeout" }`, `friendly_match_aborted` to a player who never joined).
2. **prepare**: each player locks a team with `pvp/team { uidsInSlots, leaderSlotIndex }` (validated like an arena
   attack: up to 4 owned units, leader slot; errors `UNIT_NOT_OWNED`, `NO_UNITS`, `FORMATION_TOO_LARGE`,
   `INVALID_LEADER_SLOT`, `DUPLICATE_UNITS`, `PVP_NOT_PREPARING`) within `prepareSeconds` (default 60). On timeout a
   player without a team plays with their arena defense; no usable team loses the match (`reason: "no_team"`), both
   without a team aborts it.
3. **battle**: `side_a` is the challenger, `side_b` the challenged player. Every step reaches both players as
   **`battle_frame`** (the player who sent a command gets that frame as the request answer instead). Frames have the
   `battle_pve` shape plus `matchId`, `seq` (increases with every step: drop frames you already have),
   `localSideId` (the receiver's side: its team is the `isPlayerControlled` one), `awaitingSideId` and
   `turnDeadlineUnix`; `actionOptions` / `actorOptions` only reach the player who must act, and the opponent's units
   carry no roster / rune uids. Requests (battle bucket): `battle_command { actorId, skillId, targetId }`,
   `battle_auto {}` (only the player who must act; otherwise `NOT_YOUR_TURN`), `battle_surrender {}` (any time),
   `battle_state {}` (the current frame with `snapshot: true`, after a reconnection). When the turn timer
   (`turnSeconds`, default 30) runs out the server plays the unit with the AI. Leader skills use the `arena` content
   mode. The battle-core turn order systems all work (TeamPhase: the side of the phase picks its unit).
4. **finished**: the last frame carries `result: { friendly: true, victory, winnerUserId, reason }` (`reason`:
   `elimination`, `surrender`, `forfeit`, `turn_limit`, `draw`, `no_team`); nothing is granted. The room closes 15 s
   later.

Disconnects keep the seat for `friendlyBattle.reconnectSeconds` (default 90): the opponent sees `connected: false`, the
absent player's turns are auto-played after `absentTurnDelaySeconds` (default 3), and a player not back in time loses
by forfeit (both disconnected: aborted). Leaving on purpose (`leave()`) is a surrender during the battle and aborts the
match in the lobby / prepare phases.

## GM panel API (HTTP)

The HTTP API behind the GM panel (`GET /gm`). It is not a Colyseus room. Every request needs the `x-config-api-key`
header; the access rules are in [`SECURITY.md`](SECURITY.md). The routes in the tables below are relative to
`/admin/runtime`. Errors answer `400` `{ ok: false, error: "INVALID_PAYLOAD" | "INVALID_REQUEST", detail }` (payloads
are strict zod schemas; `detail` carries the message, e.g. `Player not found.`). Every `POST` is audited on the admin
trail (`ADMIN_*`), and every player action additionally on the player's own trail (`audit_events.user_id`). `:player`
is a user id, username, email or in-game nickname (URL-encoded); the response always carries the canonical `userId`.

Transport-level answers of every `/admin` route (all JSON `{ ok: false, error }`, never an HTML page or a stack trace):

| Status | Error | When |
| --- | --- | --- |
| `401` | `UNAUTHORIZED` | the key is missing or wrong (it is read from the header only) |
| `404` | `ADMIN_DISABLED` | `CONFIG_API_KEY` is empty |
| `404` | `NOT_FOUND` | the address is outside `ADMIN_ALLOWED_IPS` |
| `429` | `ADMIN_LOCKED` | too many wrong keys from the address; sent with `Retry-After`, and the right key is refused too until the lockout ends |
| `413` | `PAYLOAD_TOO_LARGE` | the body is over `HTTP_MAX_BODY_BYTES` (64 KB by default); the config import has its own limits |
| `400` | `INVALID_JSON` | the body cannot be parsed |
| `415` | `UNSUPPORTED_MEDIA_TYPE` | the content type is not accepted |

Config import: `POST /admin/config/import` takes `application/json` (the `config.json` alone) or `application/zip` (the
Unity export bundle: at most 50 MB compressed, 400 entries, 64 MB per entry and 256 MB in total uncompressed, no `..`
or absolute names, no symlinks; otherwise `400 INVALID_BUNDLE` or `413`). Content that fails validation answers
`400 INVALID_CONFIG` with the issues in `detail`. The answer lists the imported files; the change applies at once and
is also copied into `CONFIG_DIR`. `GET /admin/config` returns the current `config.json`.

|---|---|---|
| `GET /players/search?q=&limit=` | q (1..120, matches user id, username, email or nickname), limit (1..20) | `{ ok, results: [{ userId, username, email, name, label }] }` |
| `GET /catalog/summary` | - | `{ ok, currencies: [{ id, hasCap, rechargeable }], characters: [{ id, element, naturalStars }], runeSets: [{ id, name }], dialogues: [id] }` (panel pickers) |

| `POST /players/:player/kick` | `{ reason? }` | `{ ok, userId, connections }` |
| `POST /players/:player/ban` | `{ until?: ISO datetime (null/absent = permanent), reason? }` | `{ ok, userId, until, connections }` |

`PlayerDetail` = `{ account: { userId, username, email, isGuest, createdAt, lastLoginAt, failedLogins, lockedUntil,
ban: { active, reason, until } | null, chatMute: { active, reason, until } | null, deletionScheduledAt }, profile: { name,
iconId, level, currentExp } | null, wallet: { currencyId: amount }, roster: { bagCapacity, storageCapacity, units },
runes: { capacity, total, items }, stages, towers, story: { completed, active }, guild, arena, connections, online }`. `connections` are the presence rows never closed (a crash or restart leaves some); `online` = one of them had a heartbeat in the last minute, as in the players list. Units
(first 1000) and runes (first 2000) are capped; `runes.total` is the full count.

- **kick** revokes the access sessions (not the refresh tokens: the player may log in again) and closes the live
  connections with `disconnect_notice` (`closeCode` 4401, `reason`).
- **ban** revokes sessions and refresh tokens, disconnects the player and makes login answer `AUTH_BANNED` until `until`
  (`until` must be in the future). **unban** clears flag, reason and end date.
- **mute** blocks every chat channel (global and guild: `send` answers `MUTED` with `muteUntilUnix`, `history` reports
  it). Stored in `users.chat_muted_until`; a permanent mute is stored as a date 100 years ahead. A process caches the
  value for up to 15 s, so a mute set from another server process may take that long to apply.
- **currency** sets an exact balance (credit or debit of the difference, in one transaction) and pushes the wallet
  with `player_grant`. A raise stops at the cap of a currency that cannot overflow: `clamped: true`, `balance` <
  `requested`.
- **level** sets the account level and resets its EXP to 0 without level-up rewards (the client sees it on next login).
- **story/reset** deletes the completed rows (and the in-progress one) of the scope so the sequences replay and their
  rewards can be earned again. `tutorial` / `story` match ids starting with `tutorial_` / `story_`; explicit ids must
  exist in `dialogues.json` (unless `allowUnknownDialogues`).

- **analytics** is computed from existing tables (no extra writes): `newAccounts` (`users.created_at`),
  `activePlayers` (distinct players with a presence session or a `LOGIN` audit row that day), `logins`, `pveBattles`
  (VICTORY / DEFEAT), `arenaBattles` (finished), `mailDelivered` (`user_mail` rows created), `shopPurchases` and
  `shopSpent` (`SHOP_PURCHASE` audit; the series is in `shopSpentCurrency`, the most spent currency of the period) and
  `gmCurrencyGranted` (`GM_GRANT_CURRENCY` amounts); `battles` is PvE + arena. `dates` are UTC days (oldest first,
  grouped on the database clock). `totals[metric]` = `{ value, previous, delta }` against the previous period of the
  same length; for `activePlayers` the value is the distinct count of the whole period. Audit rows older than
  `RETENTION_AUDIT_DAYS` are gone, so long periods of audit-based series may read low.
- **players** `online` = a presence heartbeat in the last 60 s. Counters ignore the search term.
- **rename** uses the in-game rules (`config.json > profile.nickname`, unique names). **mail** validates the rewards
  like the broadcast does and lands in the inbox as category `gm`.
- **units/set** keeps awakening and skills; changing `stars` resets the level to 1 (send `level` too to choose), and the
  level must fit the star tier of `config.json > gameplay` (1..max level of that tier). **units/delete** puts the
  runes it wears back in the inventory first and refuses a unit of the arena defense team. **runes/delete** takes the
  rune off its unit first (locked runes included; no refund). Both refuse units / runes of another player.
- **guild/remove** (and `POST /guilds/:id/*`) reuse the guild rules: a leader leaving hands the lead to the oldest
  officer, else the oldest member; the guild disappears when nobody is left. Kicked members get the usual guild mail and
  the guild chat posts its system line. **disband** mails every member the "removed from guild" notice. **update**
  renames with the creation rules (`GUILD_NAME_INVALID`, `GUILD_NAME_TAKEN`).
- **sessions/revoke** revokes the access sessions *and* the refresh tokens (every device) and closes the live
  connections; unlike a ban the player can log in again.
- **logs** (GM panel "Logs"): every `createLogger` call, `console.*`, Colyseus' own logger, warnings, unhandled
  rejections and uncaught exceptions are recorded by the log sink (`src/shared/log`): an in-memory ring buffer
  (`LOG_BUFFER_SIZE`, default 2000) plus batched inserts into `server_logs` (never blocks or throws into the caller; a
  failing database backs off and is reported once a minute as a memory-only `LogSink` entry; identical consecutive lines
  are folded into one entry with `repeats`; floods are capped at 300 new entries per second except errors). `scope` is the
  `[Tag]` prefix (`console` when a raw message has none). Entries older than `LOG_RETENTION_DAYS` (default 14) are purged
  by the daily retention job. The terminal prints according to `LOG_CONSOLE` (`none` default: one boot line only, plus
  fatal crashes; `error`; `all` = the classic console output). `LOG_LEVEL` is the lowest level recorded. Unhandled
  rejections are logged and do not stop the process; an uncaught exception still shuts the server down.
- **chat/messages/delete** removes the stored line; clients that already received it keep it until they reconnect.
  Muting a sender is `POST /players/:player/mute`.
- **reports**: `ReportRow` = `{ id, status, category, source, comment, reporter: { userId, username, name }, target:
  { userId, username, name }, openAgainstTarget, createdAt, handledAt, resolutionAction }` (`reporter.userId` is null
  once that account was purged). `context` holds the target's chat lines copied by the server when the report was
  filed, `messageText` the reported line. **resolve** applies the action once through the existing tools (`warn` sends
  a GM mail whose body is `message`; `mute` takes `muteHours` and works like `/players/:player/mute`; `kick`; `ban`
  takes `banDays`, with `message` as the reason shown to the player), closes the report(s) and writes `GM_REPORT_RESOLVE` on the
  target's audit trail (`GM_REPORT_DISMISS` for dismissals; the sanction itself is audited as usual). A report is
  claimed with `WHERE status = 'open'`, so a report handled twice answers `400 INVALID_REQUEST` ("already handled")
  and a failed sanction puts the report back to open. With `notifyReporter` and an action other than `none` each
  reporter gets one "thanks" mail. The bulk routes act on all open reports against one player (the sanction is
  applied once). `GET /status` also carries `reports: { open }` (null when unreadable) for the sidebar badge.
- **mail/history** `broadcasts` lists `mail_broadcasts` with `recipients` = inboxes that already received it (receipts)
  and `active` (not expired / revoked). **revoke** deletes the broadcast: inboxes that have not received it never
  will; copies already delivered stay. `direct` are the single-player GM mails (audit `GM_MAIL`, newest first).
- **config/files** is a read-only description of `game_config/*.json` (snapshots and bundles excluded): `counts` has
  the length of the top-level arrays and the key count of the top-level objects.

The panel itself (`GET /gm`) is a single offline HTML document (no CDN, fonts or external requests); it stores the
admin key only in the browser's `localStorage` and escapes every player-provided string.
